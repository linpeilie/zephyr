使用 ARM Coresight STM 的多域日志记录 (Multi-domain logging using ARM Coresight STM)
####################################################################################

Arm CoreSight SoC-400 是一个用于在系统内创建调试和跟踪功能的综合组件库。STM(系统跟踪宏单元)是一个集成到 CoreSight 系统中的跟踪源,主要设计用于嵌入到软件中的仪器的高带宽跟踪。此仪器由对 STMESP(STM 扩展激励端口)外设寄存器的内存映射写入组成。多个核心可以共享并直接访问 STM 而不会意识到彼此。每个核心有 65536 个激励端口(相同的寄存器集),可以独立访问,因此当各种上下文想要记录数据时不需要锁定。(The Arm CoreSight SoC-400 is a comprehensive library of components for the creation of debug and trace functionality within a system. The STM (System Trace Macrocell) is a trace source that is integrated into a CoreSight system, designed primarily for high-bandwidth trace of instrumentation embedded into software. This instrumentation is made up of memory-mapped writes to the STMESP (STM Extended Stimulus Port) peripheral registers. Multiple cores can share and directly access the STM without being aware of each other. Each core has 65536 stimulus ports (identical register sets) which can be independently accessed thus there is no need for locking when various contexts want to log the data.)

STM 扩展激励端口(STMESP)(STM Extended Stimulus Port (STMESP))
*************************************************************

本地域(每个核心)可以访问自己的一组 STMESP 外设。每个集合都有用于写入数据(带或不带时间戳以及带或不带标记)和写入标志的寄存器。每次对 STMESP 寄存器的写入都会将用户数据编码到 MIPI 系统跟踪协议 v2(STPv2)中。硬件通过在必要时将 Major 和 Channel 操作码添加到流中来管理来自不同 STMESP 寄存器集和不同核心的数据的复用。时间戳(来自所有核心的公共源)和同步操作码由 STM 自主添加。(Local domain (each core) has access to its own set of STMESP peripherals. Each set has registers for writing data (with or without timestamp and with or without marking) and writing a flag. Each write to STMESP register results in the user data being encoded into MIPI System Trace Protocol v2 (STPv2). Hardware manages multiplexing of data from different STMESP register sets and from different cores by adding Major and Channel opcodes into the stream when necessary. Timestamp (from common source for all cores) and synchronization opcodes are autonomously added by the STM.)

STM 生成的数据流可以最终到达各种接收器。例如,它可以直接发送到 TPIU(跟踪端口接口单元)或保存在称为 ETR(嵌入式跟踪路由器)的 RAM 循环缓冲区中。TPIU 是一个 5 针接口(4 个数据引脚和时钟),需要外部工具来捕获数据(例如 J-Trace PRO)。当使用 ETR 时,系统中的一个核心负责处理该数据,例如通过 UART 将其转储到主机。(Data stream generated by STM can end up in various sinks. For example it can be directly send to TPIU (Trace Port Interface Unit) or saved in the RAM Circular Buffer which is called ETR (Embedded Trace Router). TPIU is a 5 pin interface (4 data pins and clock) and external tool is required to capture the data (e.g. J-Trace PRO). When ETR is used then one core in the system is responsible for processing that data, for example dumping it over UART to the host.)

ARM Coresight 嵌入式跟踪路由器(ETR)(ARM Coresight Embedded Trace Router (ETR))
******************************************************************************

ETR 是一个循环 RAM 缓冲区,跟踪数据保存到其中。由于它可能包含来自各种源的数据,因此使用额外的包装协议来复用它们。为此使用 ``Coresight 跟踪格式化器``。数据被编码成 16 字节帧,其中最多包含 15 字节的数据。循环 RAM 缓冲区大小限制为 4k,因此存在数据溢出的风险。如果发生溢出,则数据丢失,但由于 STPv2 数据流中存在同步操作码,可以恢复同步。(ETR is a circular RAM buffer to which tracing data is saved. Since it may contain data from various sources additional wrapping protocol is used to multiplex them. ``Coresight Trace Formatter`` is used for that. Data is encoded into 16 bytes frames which holds up to 15 byte of data. Circular RAM buffer size is limited to 4k thus there is a risk of data overflow. If overflow occurs then data is lost but due to presence of synchronization opcodes in the STPv2 data stream synchronization can be restored.)

来自 ETR 的数据在设备上处理。它可以按原样转发到主机(例如使用 UART),主机工具在那里解码数据,或者可以在芯片上解码数据以以人类可读的格式输出数据。(Data from ETR is handled on the device. It can be forwarded as-is to the host (e.g. using UART), where a host tool is decoding the data or data can be decoded on-chip to output the data in human readable format.)

Nordic Semiconductor NRF54H20 实现使用自己的包装器:跟踪缓冲区监视器(TBM),而不是使用 ETR 外设来获取缓冲区忙碌状态。(Nordic Semiconductor NRF54H20 implementation instead of using ETR peripheral for getting buffer busyness is using own wrapper: Trace Buffer Monitor (TBM).)

STMESP 日志记录前端 (STMESP Logging frontend)
*********************************************

实现了 :ref:`log_frontend` API。自定义前端假定所有必需的操作都在日志记录宏调用的上下文中执行。还假定前端提供时间戳。前端利用存在多个 STMESP 寄存器集的事实,并使用多个集合来避免锁定上下文。原子递增的通道计数器用于选择唯一的 STMESP 集合,整个消息都写入该 STMESP。使用有限的集合池,将大多数通道留给其他用途。(:ref:`log_frontend` API is implemented. Custom frontend assumes that all required operations are executed in the context of the logging macro call. It is also assumed that frontend provides the timestamp. Frontend utilizes a fact that there are multiple STMESP register sets and use multiple sets to avoid locking context. The atomically incremented channel counter is used to pick unique STMESP set and whole message is written to that STMESP. Limited pool of sets is used leaving most of channels for other purposes.)

早期日志记录 (Early logging)
=============================

在 STM 或 ETR/TPIU 设置之前,不能使用 STMESP。为了支持早期日志记录,在基础设施准备就绪之前,使用专用的 RAM 缓冲区来写入数据。当通知 STM 基础设施就绪(:c:func:`log_frontend_stmesp_etr_ready`)时,RAM 缓冲区内容将写入 STMESP。早期日志记录仅适用于拥有并配置 Coresight 基础设施的核心(例如,在 NRF54H20 的情况下,它是安全核心)。(STMESP cannot be used before STM or ETR/TPIU is setup. In order to support early logging, before infrastructure is ready a dedicated RAM buffer is used to which data is written. When STM infrastructure readiness is notified (:c:func:`log_frontend_stmesp_etr_ready`) then RAM buffer content is written to STMESP. Early logging is applicable only to the core which owns and configures Coresight infrastructure (e.g. in case of NRF54H20 it is the Secure core).)

跟踪点 (Trace points)
======================

可能存在日志记录太慢的情况(即使它非常快)。对于这样的情况,添加了专用的 ``跟踪点`` API。它非常快,因为它只是对一个 STMESP 寄存器的单次写入。API 中有 2 个函数:(There may be cases when logging is too slow (even though it is very fast). For cases like that a dedicated ``trace point`` API is added. It is extremely fast because it is just a single write to one STMESP register. There are 2 functions in the API:)

* :c:func:`log_frontend_stmesp_tp` - 它接受单个参数 - 索引。索引在 0 到 65280 之间。(It accepts single argument - index. Index is between 0 and 65280.)
* :c:func:`log_frontend_stmesp_tp_d32` - 它接受两个参数 - 索引和用户数据。索引在 0 到 65280 之间。用户数据是 32 位字。(It accepts two arguments - index and user data. Index is between 0 and 65280. User data is 32 bit word.)

在 NRF54H20 上记录单个跟踪点所需的时间不到 100 纳秒,比最快的日志消息快约 7 倍。(It takes less than 100 ns to log a single trace point on NRF54H20 and it is approx. 7 times faster than the fastest log message.)

使用 STM 进行日志记录 (Logging using STM)
*****************************************

STM 日志记录有 2 种操作模式:(STM logging has 2 modes of operations:)

* 基于字典 - 辅助模式,使用基于字典的日志记录。在此模式下,日志记录字符串可以从二进制文件中删除,因为它们仅用于解码,而解码由主机工具执行。此模式占用更少的内存并且更快(快 2-3 倍)。写入的数据更少,因此 ETR 缓冲区中数据溢出的机会更少。(Dictionary-based - assisted mode which is using dictionary-based logging. In this mode logging strings can be removed from the binary because they are only needed for decoding and decoding is performed by the host tool. This mode takes less memory and is faster (2-3 times faster). There is less data written so there is less chance of data overflow in ETR buffer.)
* 独立 - 数据在芯片上解码,并打印人类可读的字符串。此模式需要更多的设备资源和处理能力。(Standalone - data is decoded on chip and human-readable strings are printed. This mode requires more device resources and processing power.)

每个核心(本地域)使用将日志数据写入 STMESP 寄存器的日志记录前端。(Each core (local domain) is using logging frontend which writes logging data to STMESP registers.)

如果使用 TPIU 作为输出,则不需要更多软件组件。STPv2 数据流由 STM 组成并通过 TPIU 发送。(If TPIU is used as the output then there is no more software components needed. STPv2 stream of data is composed by STM and send over TPIU.)

如果使用 ETR RAM 缓冲区,则缓冲区所有者核心(``代理``)负责处理该数据。如果使用基于字典的日志记录,则代理只是按原样通过 UART 发送数据。如果使用独立日志记录,则代理使用 :ref:`cs_trace_defmt` 和 :ref:`mipi_stp_decoder` 来解码数据和解复用消息。使用日志记录 :ref:`log_output` 将消息格式化为人类可读的字符串。(If ETR RAM buffer is used then buffer owner core (``proxy``) is responsible for handling that data. If dictionary-based logging is used then proxy just sends data as-is over UART. If standalone logging is used then proxy is using :ref:`cs_trace_defmt` and :ref:`mipi_stp_decoder` to decode data and demultiplex messages. Messages are formatted to human readable strings using logging :ref:`log_output`.)

基于字典的日志记录 (Dictionary-based logging)
==============================================

辅助多核日志记录使用基于字典的日志记录将消息发送到 STM 而不包含冗余字符串,基于 Zephyr 提供的日志记录 API 的 :ref:`logging_guide_dictionary` 功能。它不在日志消息中包含格式字符串,而是记录存储字符串的地址(消息 ID),这减少了日志记录子系统的大小。如果数据进入 ETR 缓冲区,则代理核心的责任是转储此数据。配备解码器工具的主机 PC 使用在构建过程中生成的 JSON 数据库将这些地址转换回人类可读的文本。(Assisted multicore logging uses dictionary-based logging to send messages without redundant strings to STM, and is based on the :ref:`logging_guide_dictionary` feature of the logging API provided by Zephyr. Instead of including the format strings in the log messages, it logs the addresses (message IDs) where the strings are stored, which reduces the size of the logging subsystem. If the data goes to the ETR buffer, the proxy core's responsibility is to dump this data. The host PC, equipped with a decoder tool, translates these addresses back into human-readable text using a JSON database generated during the build process.)

使用日志时,此方法具有以下优点:(When using logs, this method has the following advantages:)

* 它减少了二进制文件的大小,因为日志消息中使用的字符串不存储在二进制文件本身中。日志记录基础设施也非常有限。在本地域上,它只是前端。甚至不需要字符串格式化函数。(It reduces the size of the binary, as the strings used in the log messages are not stored in the binary itself. Logging infrastructure is also very limited. On local domains it is just the frontend. There is even no need to have string formatting function.)
* 它减少了需要发送到应用程序核心并由其处理的数据量,因为字符串格式化卸载到主机端。(It reduces the amount of data that needs to be sent to and processed by the application core, as the string formatting is offloaded to the host side.)
* 日志记录很快。在 NRF54H20 上记录简单消息(最多 2 个参数)所需的时间不到 1 微秒。(Logging is fast. It takes less than 1 us to log a simple message (up to 2 arguments) on NRF54H20.)

代理核心使用 Nordic 特定的外设(TBM)来获取 ETR 缓冲区忙碌状态并通过 UART 发送数据。用于 ETR 缓冲区的 Nordic 特定驱动程序位于 :zephyr_file:`drivers/debug/debug_nrf_etr.c`。(Proxy core is using Nordic specific peripheral (TBM) to get ETR buffer busyness and send data over UART. Nordic specific driver for ETR buffer is located in :zephyr_file:`drivers/debug/debug_nrf_etr.c`.)

配置 (Configuration)
--------------------

对于 Nordic SoC,应使用专用代码片段(:ref:`nordic-log-stm-dict`)来启用日志记录。每个核心都应使用该代码片段构建。如果任何核心想要使用它,则应用程序核心也需要启用它,因为它充当代理(ETR 缓冲区处理)。所有核心必须使用相同的日志记录配置。(For Nordic SoC a dedicated snippet (:ref:`nordic-log-stm-dict`) shall be used to enable logging. Each core shall be build with that snippet. If any core wants to use it then application core is required to have it enabled too since it acts as the proxy (ETR buffer processing). All cores must use the same configuration of the logging.)

读取日志 (Reading the logs)
---------------------------

要读取基于字典的 STM 日志输出,请执行以下操作:(To read the dictionary-based STM log output, do the following:)

1. 设置日志捕获。(Set up the log capture.)

   使用 ``nrfutil trace stm`` 命令开始从设备捕获日志,为每个域 ID 指定数据库配置,以及串口、波特率和输出文件名::(Use the ``nrfutil trace stm`` command to start capturing logs from the device, specifying the database configuration for each domain ID, as well as the serial port, the baud rate, and the output file name::)

      nrfutil trace stm --database-config 34:build/zephyr/log_dictionary.json,35:build_rad/zephyr/log_dictionary.json --input-serialport /dev/ttyACM1 --baudrate 115200 --output-ascii out.txt

#. 捕获和解码日志。(Capture and decode the logs.)

   nrfutil 将从指定的 UART 端口捕获日志数据,并使用提供的字典数据库将日志解码为人类可读的格式。解码的日志将保存在指定的输出文件中(前面示例中的 :file:`out.txt` 文件)。(nrfutil will capture the log data from the specified UART port and use the provided dictionary databases to decode the logs into a human-readable format. The decoded logs will be saved in the specified output file (the :file:`out.txt` file in the previous example).)

#. 打开输出文件以查看解码的日志消息。(Open the output file to review the decoded log messages.)

   该文件将包含时间戳和人类可读格式的日志消息。(The file will contain timestamps and the log messages in a format that is human-readable.)

如果日志捕获无法找到同步,请重新运行捕获过程。(If the log capture fails to find a sync, rerun the capture process.)

.. note::
   重新运行进程时可能会出现解码伪影或不正确的时间戳。(Decoding artifacts or incorrect timestamps might occur when rerunning the process.)

每条日志行在日志级别和模块名称之间包含与域相关或与核心相关的前缀,指示生成日志条目的核心。以下是用于指示核心的前缀:(Each log line contains a domain-related or core-related prefix between the log level and the module name, indicating the core that generated the log entry. The following are the prefixes used to indicate the cores:)

独立日志记录 (Stand-alone logging)
===================================

前端正在写入 STMESP 寄存器。消息格式与 :zephyr_file:`subsys/logging/frontends/log_frontend_stmesp_demux.c` 中的片上解码器对齐。(Frontend is writing to STMESP registers. Message format is aligned with the on chip decoder in :zephyr_file:`subsys/logging/frontends/log_frontend_stmesp_demux.c`.)

``代理``使用 Nordic 特定的外设(TBM)来获取 ETR 缓冲区忙碌状态,并读取和解码数据,并通过 UART 发送人类可读的数据。用于 ETR 缓冲区的 Nordic 特定驱动程序位于 :zephyr_file:`drivers/debug/debug_nrf_etr.c`。它使用 :ref:`cs_trace_defmt` 和 :ref:`mipi_stp_decoder` 以及上述解复用器来解码消息。(``Proxy`` is using Nordic specific peripheral (TBM) to get ETR buffer busyness and read and decode data and send human-readable data over UART. Nordic specific driver for ETR buffer is located in :zephyr_file:`drivers/debug/debug_nrf_etr.c`. It is using :ref:`cs_trace_defmt` and :ref:`mipi_stp_decoder` and above-mentioned demultiplexer to decode messages.)

日志记录消息包含日志记录宏中使用的只读格式字符串,因此无法从二进制文件中删除它们。此模式使用更多只读内存并且吞吐量较低,因为消息更长并且处理耗时。与基于字典的模式相比,日志记录慢 2-3 倍。(Logging messages contains read-only format string used in the logging macros thus they cannot be removed from the binary. This mode uses more read-only memory and has lower throughput because messages are longer and processing is time consuming. Compared to the dictionary-based mode logging is 2-3 slower.)

* 使用多个域(例如无线核心和应用核心)时,确保每个数据库都以正确的域 ID 为前缀。(When working with multiple domains, such as the Radio core and Application core, ensure that each database is prefixed with the correct domain ID.)

STM Extended Stimulus Port (STMESP)
***********************************

Local domain (each core) has access to its own set of STMESP peripherals. Each set has registers for writing data (with or without timestamp and with or without marking) and writing a flag. Each write
to STMESP register results in the user data being encoded into MIPI System Trace Protocol v2 (STPv2).
Hardware manages multiplexing of data from different STMESP register sets and from different cores
by adding Major and Channel opcodes into the stream when necessary. Timestamp (from common source for all cores) and synchronization opcodes are autonomously added by the STM.

Data stream generated by STM can end up in various sinks. For example it can be directly send to
TPIU (Trace Port Interface Unit) or saved in the RAM Circular Buffer which is called ETR (Embedded
Trace Router). TPIU is a 5 pin interface (4 data pins and clock) and external tool is required to
capture the data (e.g. J-Trace PRO).
When ETR is used then one core in the system is responsible for processing that data, for example
dumping it over UART to the host.

ARM Coresight Embedded Trace Router (ETR)
*****************************************

ETR is a circular RAM buffer to which tracing data is saved. Since it may contain data from
various sources additional wrapping protocol is used to multiplex them. ``Coresight Trace
Formatter`` is used for that. Data is encoded into 16 bytes frames which holds up to 15 byte
of data. Circular RAM buffer size is limited to 4k thus there is a risk of data overflow. If
overflow occurs then data is lost but due to presence of synchronization opcodes in the STPv2
data stream synchronization can be restored.

Data from ETR is handled on the device. It can be forwarded as-is to the host (e.g. using UART),
where a host tool is decoding the data or data can be decoded on-chip to output the data in human readable format.

Nordic Semiconductor NRF54H20 implementation instead of using ETR peripheral for getting
buffer busyness is using own wrapper: Trace Buffer Monitor (TBM).

STMESP Logging frontend
***********************

:ref:`log_frontend` API is implemented. Custom frontend assumes that all required operations are executed in the context of the logging macro call. It is also assumed that frontend provides the timestamp. Frontend utilizes a fact that there are multiple STMESP register sets and use multiple sets to avoid locking context. The atomically incremented channel counter is used to pick unique STMESP set and
whole message is written to that STMESP. Limited pool of sets is used leaving most of channels for
other purposes.

Early logging
=============

STMESP cannot be used before STM or ETR/TPIU is setup. In order to support early logging,
before infrastructure is ready a dedicated RAM buffer is used to which data is written. When
STM infrastructure readiness is notified (:c:func:`log_frontend_stmesp_etr_ready`) then RAM buffer
content is written to STMESP. Early logging is applicable only to the core which owns and configures
Coresight infrastructure (e.g. in case of NRF54H20 it is the Secure core).

Trace points
============

There may be cases when logging is too slow (even though it is very fast). For cases like that a dedicated ``trace point`` API is added. It is extremely fast because it is just a single
write to one STMESP register. There are 2 functions in the API:

* :c:func:`log_frontend_stmesp_tp` - It accepts single argument - index. Index is between
  0 and 65280.
* :c:func:`log_frontend_stmesp_tp_d32` - It accepts two arguments - index and user data.
  Index is between 0 and 65280. User data is 32 bit word.

It takes less than 100 ns to log a single trace point on NRF54H20 and it is approx. 7 times faster than the fastest log message.

Logging using STM
*****************

STM logging has 2 modes of operations:

* Dictionary-based - assisted mode which is using dictionary-based logging. In this mode logging
  strings can be removed from the binary because they are only needed for decoding and decoding
  is performed by the host tool. This mode takes less memory and is faster (2-3 times faster).
  There is less data written so there is less chance of data overflow in ETR buffer.
* Standalone - data is decoded on chip and human-readable strings are printed. This mode requires
  more device resources and processing power.

Each core (local domain) is using logging frontend which writes logging data to STMESP registers.

If TPIU is used as the output then there is no more software components needed. STPv2 stream
of data is composed by STM and send over TPIU.

If ETR RAM buffer is used then buffer owner core (``proxy``) is responsible for handling that data.
If dictionary-based logging is used then proxy just sends data as-is over UART.
If standalone logging is used then proxy is using :ref:`cs_trace_defmt` and
:ref:`mipi_stp_decoder` to decode data and demultiplex messages. Messages are formatted to human
readable strings using logging :ref:`log_output`.

Dictionary-based logging
========================

Assisted multicore logging uses dictionary-based logging to send messages without redundant strings
to STM, and is based on the :ref:`logging_guide_dictionary` feature of the logging API provided by
Zephyr.
Instead of including the format strings in the log messages, it logs the addresses (message IDs)
where the strings are stored, which reduces the size of the logging subsystem.
If the data goes to the ETR buffer, the proxy core's responsibility is to dump this data.
The host PC, equipped with a decoder tool, translates these addresses back into human-readable text
using a JSON database generated during the build process.

When using logs, this method has the following advantages:

* It reduces the size of the binary, as the strings used in the log messages are not stored in the binary itself. Logging infrastructure is also very limited. On local domains it is just the frontend. There is even no need to have string formatting function.
* It reduces the amount of data that needs to be sent to and processed by the application core, as the string formatting is offloaded to the host side.
* Logging is fast. It takes less than 1 us to log a simple message (up to 2 arguments) on NRF54H20.

Proxy core is using Nordic specific peripheral (TBM) to get ETR buffer busyness and send data over
UART. Nordic specific driver for ETR buffer is located in
:zephyr_file:`drivers/debug/debug_nrf_etr.c`.

Configuration
-------------

For Nordic SoC a dedicated snippet (:ref:`nordic-log-stm-dict`) shall be used to enable logging.
Each core shall be build with that snippet. If any core wants to use it then application core is
required to have it enabled too since it acts as the proxy (ETR buffer processing). All cores must use the same configuration of the logging.

Reading the logs
----------------

To read the dictionary-based STM log output, do the following:

1. Set up the log capture.

   Use the ``nrfutil trace stm`` command to start capturing logs from the device, specifying the database configuration for each domain ID, as well as the serial port, the baud rate, and the output file name::

      nrfutil trace stm --database-config 34:build/zephyr/log_dictionary.json,35:build_rad/zephyr/log_dictionary.json --input-serialport /dev/ttyACM1 --baudrate 115200 --output-ascii out.txt

#. Capture and decode the logs.

   nrfutil will capture the log data from the specified UART port and use the provided dictionary databases to decode the logs into a human-readable format.
   The decoded logs will be saved in the specified output file (the :file:`out.txt` file in the previous example).

#. Open the output file to review the decoded log messages.

   The file will contain timestamps and the log messages in a format that is human-readable.

If the log capture fails to find a sync, rerun the capture process.

.. note::
   Decoding artifacts or incorrect timestamps might occur when rerunning the process.

Each log line contains a domain-related or core-related prefix between the log level and the module name, indicating the core that generated the log entry.
The following are the prefixes used to indicate the cores:

.. csv-table:: nRF54H20 log prefixes
   :header: "Core", "Prefix", "ID"

   Secure Domain, ``sec``, 0x21
   Application core, ``app``, 0x22
   Radio core, ``rad``, 0x23
   System Controller (SysCtrl), ``sys``, 0x2c
   Fast Lightweight Processor (FLPR), ``flpr``, 0x2d
   Peripheral Processor (PPR), ``ppr``, 0x2e
    , ``mod``, 0x24

Stand-alone logging
===================

Frontend is writing to STMESP registers. Message format is aligned with the on chip decoder
in :zephyr_file:`subsys/logging/frontends/log_frontend_stmesp_demux.c`.

``Proxy`` is using Nordic specific peripheral (TBM) to get ETR buffer busyness and read and
decode data and send human-readable data over UART. Nordic specific driver for ETR buffer is
located in :zephyr_file:`drivers/debug/debug_nrf_etr.c`. It is using :ref:`cs_trace_defmt` and
:ref:`mipi_stp_decoder` and above-mentioned demultiplexer to decode messages.

Logging messages contains read-only format string used in the logging macros thus they cannot be
removed from the binary. This mode uses more read-only memory and has lower throughput because
messages are longer and processing is time consuming. Compared to the dictionary-based mode logging
is 2-3 slower.

Additional considerations
=========================

When using STM logging, consider the following:

* Use optimized log macros (having up to 2 word size numeric arguments, like ``LOG_INF("%d %c", (int)x, (char)y)``) to improve the size and speed of logging.
* For memory constrained applications (for example, when running on the PPR core), disable the ``printk()`` function by setting both the :kconfig:option:`CONFIG_PRINTK` and :kconfig:option:`CONFIG_BOOT_BANNER` Kconfig options to ``n`` in your project configuration.
* When working with multiple domains, such as the Radio core and Application core, ensure that each database is prefixed with the correct domain ID.
* Some log messages might be dropped due to the limited size of the RAM buffer that stores STM logs.
