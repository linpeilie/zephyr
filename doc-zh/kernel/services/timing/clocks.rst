.. _kernel_timing:

内核计时
########

Zephyr 提供了一个强大且可扩展的计时框架,能够从任意精度的硬件计时源报告和跟踪
定时事件。

时间单位
========

内核时间以几种用于不同目的的单位进行跟踪。

实时值,通常以毫秒或微秒指定,是向应用程序代码呈现时间的默认方式。它们具有普遍
可移植和普遍理解的优点,尽管它们可能无法完全匹配底层硬件的精度。

内核通过 :c:func:`k_cycle_get_32` 和 :c:func:`k_cycle_get_64` API 呈现"周期"
计数。其意图是此计数器表示操作系统能够向用户呈现的最快周期计数器(例如,CPU
周期计数器),并且读取操作非常快。期望非常敏感的应用程序代码可能以轮询方式使用
它来实现最大精度。此计数器的频率需要随时间稳定,并可从
:c:func:`sys_clock_hw_cycles_per_sec` 获得(在几乎所有平台上,这是一个运行时
常量,求值为 CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC)。

对于异步计时,内核定义了"滴答"概念。"滴答"是内核执行所有内部正常运行时间和
超时记账的内部计数。中断预期在滴答边界上传递(在实际情况下尽可能),并且不跟踪
分数滴答。滴答率的选择可通过 :kconfig:option:`CONFIG_SYS_CLOCK_TICKS_PER_SEC`
配置。大多数硬件平台(支持设置任意中断超时的平台)的默认值预期在 10 kHz 范围内,
软件仿真平台和旧驱动程序使用更传统的 100 Hz 值。

转换
----

Zephyr 为所有时间单位提供了具有舍入控制的详尽枚举转换库。"ms"(毫秒)、
"us"(微秒)、"tick"或"cyc"的任何单位都可以转换为任何其他单位。提供舍入控制,
每个转换都有"floor"(向下舍入到最接近的输出单位)、"ceil"(向上舍入)和
"near"(舍入到最接近)可用。最后,输出精度可以指定为 32 或 64 位。

例如::c:func:`k_ms_to_ticks_ceil32` 将毫秒输入值转换为下一个更高的滴答数,
返回截断为 32 位精度的结果;:c:func:`k_cyc_to_us_floor64` 将测量的周期计数
转换为已过去的微秒数,具有完整的 64 位精度。有关转换例程的完整枚举,请参阅
参考文档。

在大多数平台上,各种计数器速率是彼此的整数倍,并且输出适合单个字,这些转换
扩展为 2-4 个操作序列,仅在实际需要和请求时才需要完全精度。

.. _kernel_timing_uptime:

正常运行时间
============

内核代表应用程序跟踪系统正常运行时间计数。这可以随时通过 :c:func:`k_uptime_get`
获得,它提供自系统启动以来的毫秒正常运行时间值。这预期是大多数可移植应用程序
代码使用的实用程序。

然而,内部跟踪是作为 64 位整数滴答计数。具有精确计时要求(愿意进行自己转换为
可移植实时单位)的应用程序可以使用 :c:func:`k_uptime_ticks` 访问它。

超时
====

Zephyr 内核提供了许多带有"超时"参数的 API。从概念上讲,这表示事件将发生的时间。
例如:

* 内核阻塞操作(如 :c:func:`k_sem_take` 或 :c:func:`k_queue_get`)可能提供
  超时,如果没有数据可用,则例程将在该超时后返回错误代码。

* 内核 :c:struct:`k_timer` 对象必须为其持续时间和周期指定延迟。

* 内核 :c:struct:`k_work_delayable` API 提供超时参数,指示何时将工作队列项
  添加到系统队列。

所有这些值都使用 :c:type:`k_timeout_t` 值指定。这是一个不透明的结构类型,
必须使用内核超时宏系列之一进行初始化。最常见的 :c:macro:`K_MSEC` 定义当前
时间后的毫秒时间。

相对超时的"当前时间"含义取决于上下文:

* 从超时回调中调度相对超时时(例如,从传递给 :c:func:`k_timer_init` 的到期
  函数或传递给 :c:func:`k_work_init_delayable` 的工作处理程序中),即使"实时"
  将已经推进,"当前时间"也是当前触发超时最初计划的确切时间。这是为了确保从
  另一个定时器的回调中调度的定时器将始终以与触发定时器的精确偏移量计算。
  因此可以以固定间隔触发而不会随时间引入系统时钟漂移。

* 从应用程序上下文调度超时时,"当前时间"表示内核接收超时值时
  :c:func:`k_uptime_ticks` 返回的值。

超时初始化的其他选项遵循上述单位约定::c:macro:`K_NSEC()`、:c:macro:`K_USEC`、
:c:macro:`K_TICKS` 和 :c:macro:`K_CYC()` 分别指定在指定数量的纳秒、微秒、
滴答和周期后到期的超时值。

:c:type:`k_timeout_t` 值的精度是可配置的,默认为 32 位。非滴答单位的大正常
运行时间计数将经历复杂的翻转语义,因此预期具有长正常运行时间的计时敏感应用程序
将配置为使用 64 位超时类型。

最后,可以将超时指定为自系统启动以来的绝对时间。使用 :c:macro:`K_TIMEOUT_ABS_MS`
初始化的超时表示当系统正常运行时间达到指定值后到期的超时。此 API 还有纳秒、
微秒、周期和滴答变体。

计时内部机制
============

超时队列
--------

使用上述 API 指定的所有 Zephyr :c:type:`k_timeout_t` 事件在单个全局事件队列中
管理。每个事件存储在双向链表中,并附带来自前一个事件的滴答增量计数。要对事件
采取的操作指定为请求事件的子系统提供的回调函数指针,以及预期嵌入在子系统定义的
数据结构中的 :c:struct:`_timeout` 跟踪结构(例如::c:struct:`wait_q` 结构或
:c:type:`k_tid_t` 线程结构)。

请注意,通过 :c:type:`k_timeout_t` 传递的所有变体单位在插入列表时一次性转换为
滴答。内核内部没有多次转换步骤,因此无论存在多少事件或超时可能多长,都可以在
滴答级别保证精度。

请注意,列表结构意味着管理大量超时所涉及的 CPU 工作与活动超时数量呈二次关系。
超时队列的 API 设计旨在允许更可扩展的后端数据结构,但目前不存在这样的实现。

定时器驱动程序
--------------

滴答级别的内核计时由具有相对简单 API 的定时器驱动程序驱动。

* 驱动程序预期能够通过 :c:func:`sys_clock_announce` 调用向内核"宣布"新滴答,
  该调用传递自上次宣布调用(或系统启动)以来已经过的整数滴答数。这些调用可以
  随时发生,但驱动程序预期尝试确保(在中断延迟交互实际可行的范围内)它们在
  滴答边界附近发生(即不在滴答的"中途"),最重要的是,它们随时间正确,相对于
  其他计数器和真实世界时间的偏差最小。

* 驱动程序预期向内核提供 :c:func:`sys_clock_set_timeout` 调用,指示在内核必须
  接收宣布调用以触发注册的超时之前可以经过多少滴答。在那一刻之前宣布新滴答是
  合法的(尽管它们必须是正确的),但之后的延迟将导致事件被遗漏。请注意,此处
  传递的超时值是当前时间的增量,但这并不免除驱动程序随时间提供稳定滴答率的
  要求。此函数的天真实现容易受到分数滴答被错误"重置"并导致时钟偏移的错误的
  影响。

* 驱动程序预期提供 :c:func:`sys_clock_elapsed` 调用,提供自上次调用
  :c:func:`sys_clock_announce` 以来已经过的滴答数的当前指示(与真实世界时钟
  相比),内核需要测试新到达的超时是否到期。

请注意,此 API 的自然实现导致"无滴答"内核,它仅接收和处理已注册事件的定时器
中断,依赖可编程硬件计数器提供不规则中断。但也可以轻松实现传统的"有滴答"或
"哑"计数器驱动程序:

* 驱动程序可以以与 OS 滴答率对应的固定速率接收中断,每次调用
  :c:func:`sys_clock_announce` 时参数为一。

* 驱动程序可以忽略对 :c:func:`sys_clock_set_timeout` 的调用,因为无论超时
  状态如何,每个滴答都会被宣布。

* 驱动程序可以为每次对 :c:func:`sys_clock_elapsed` 的调用返回零,因为无法
  检测到超过一个滴答的流逝(否则将接收到中断)。


SMP 细节
--------

通常,在多处理器上下文中运行时,上述定时器 API 不会改变。内核将适当地在内部
同步所有访问,并确保所有关键部分都很小且最小。但有些注意事项需要详细说明:

* Zephyr 对哪个 CPU 服务定时器中断是不可知的。让每个定时器中断都在单个处理器上
  处理并非非法(尽管在某些情况下可能不可取)。现有的 SMP 架构实现对称定时器
  驱动程序。

* :c:func:`sys_clock_announce` 调用预期在驱动程序级别全局同步。内核不执行任何
  按 CPU 跟踪,并且如果两个定时器中断几乎同时触发,则只有一个将向计时子系统
  提供当前滴答计数。如果没有滴答已经过,另一个可以合法地提供零滴答计数。它
  不应因为时间片要求而"跳过"宣布调用(见下文)。

* 某些 SMP 硬件使用单个全局定时器设备,其他硬件使用每个 CPU 计数器。此处的
  复杂性(例如:确保 CPU 之间的计数器同步)预期由驱动程序而不是内核管理。

* 通过 :c:func:`sys_clock_set_timeout` 传回驱动程序的下一个超时值对每个 CPU
  都是相同的。因此,默认情况下,每个 CPU 都会看到每个事件的同时定时器中断,
  即使根据定义它们中只有一个应该看到 :c:func:`sys_clock_announce` 的非零
  滴答参数。对于计时敏感的应用程序,这可能是正确的默认值(因为它最小化了错误的
  ISR 或中断锁延迟超时的机会),但在某些情况下可能是性能问题。当前设计期望
  任何此类优化都是定时器驱动程序的责任。

时间片
------

计时子系统的辅助工作是向调度器提供滴答计数器,以允许实现线程的时间片。线程
时间片不能是超时值,因为它不反映全局到期,而是需要在 SMP 上下文中的每个 CPU 上
独立跟踪的每个 CPU 值。

因为可能没有其他硬件可用于驱动时间片,Zephyr 复用现有的定时器驱动程序。这意味着
当当前调度时间片线程时,传递给 :c:func:`sys_clock_set_timeout` 的值可能被限制
为小于当前下一个超时的值。

保持毫秒 API 的子系统
---------------------

通常,这样的代码将像应用程序代码一样移植。来自用户的毫秒值可以以子系统喜欢的
任何方式处理,然后在呈现给内核时使用 :c:macro:`K_MSEC()` 转换为内核超时。

显然,这是以无法使用新功能为代价的,例如更高精度的超时构造函数或绝对超时。
但对于具有简单需求的许多子系统,这可能是可以接受的。

一个复杂性是 :c:macro:`K_FOREVER`。过去可能能够接受此值到其毫秒 API 的子系统
不再可以,因为它不再是整数类型。此类代码需要使用不同的整数值标记来表示"永远"。
:c:macro:`K_NO_WAIT` 当然也有同样的类型安全问题,但由于它是(并且一直是)
简单的数字零,因此它有一个自然的移植路径。

使用 ``k_timeout_t`` 的子系统
-----------------------------

理想情况下,采用"超时"参数指定等待时间的代码应尽可能使用内核本机抽象。但
:c:type:`k_timeout_t` 是不透明的,需要在应用程序检查之前进行转换。

一些转换很简单。需要测试 :c:macro:`K_FOREVER` 的代码可以简单地使用
:c:macro:`K_TIMEOUT_EQ()` 宏测试不透明结构的相等性并采取特殊操作。

更复杂的情况是子系统需要获取超时并循环,等待它完成,同时执行一些可能需要对
底层内核代码进行多个阻塞操作的处理。例如,考虑此设计:

.. code-block:: c

    void my_wait_for_event(struct my_subsys *obj, int32_t timeout_in_ms)
    {
        while (true) {
            uint32_t start = k_uptime_get_32();

            if (is_event_complete(obj)) {
                return;
            }

            /* 等待状态更改通知 */
            k_sem_take(obj->sem, timeout_in_ms);

            /* 减去已过时间 */
            timeout_in_ms -= (k_uptime_get_32() - start);
        }
    }

此代码要求检查超时值,这不再可能。对于这种情况,新 API 提供内部
:c:func:`sys_timepoint_calc` 和 :c:func:`sys_timepoint_timeout` 例程,
将任意超时转换为基于它将到期的正常运行时间滴答的时间点值并从中转换。
因此,这样的循环可能看起来像:


.. code-block:: c

    void my_wait_for_event(struct my_subsys *obj, k_timeout_t timeout)
    {
        /* 从超时计算结束时间 */
        k_timepoint_t end = sys_timepoint_calc(timeout);

        do {
            if (is_event_complete(obj)) {
                return;
            }

            /* 使用剩余时间更新超时 */
            timeout = sys_timepoint_timeout(end);

            /* 等待状态更改通知 */
            k_sem_take(obj->sem, timeout);
        } while (!K_TIMEOUT_EQ(timeout, K_NO_WAIT));
    }

请注意,:c:func:`sys_timepoint_calc` 接受特殊值 :c:macro:`K_FOREVER` 和
:c:macro:`K_NO_WAIT`,并且对于绝对超时也完全相同。相反,如果使用这些值创建
时间点,:c:func:`sys_timepoint_timeout` 可能返回 :c:macro:`K_FOREVER` 或
:c:macro:`K_NO_WAIT`,如果时间点现在在过去,也会返回后者。对于简单情况,
也可以使用 :c:func:`sys_timepoint_expired`。

但是使用这些的子系统仍然需要注意。请注意,增量超时需要相对于"当前时间"解释,
显然该时间是调用 :c:func:`sys_timepoint_calc` 的时间。但用户期望时间是他们
将超时传递给您的时间。必须注意只调用此函数一次,尽可能与用户代码中的超时
创建同步。它不应用于"存储的"超时值,并且永远不应在循环中迭代调用。
