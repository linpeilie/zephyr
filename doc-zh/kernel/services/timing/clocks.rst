.. _kernel_timing:

内核时间管理
############

Zephyr 提供了一个强大且可扩展的时间管理框架，以启用从任意精度的硬件时间源报告和跟踪定时事件。

时间单位
========

内核时间在几个单位中进行跟踪，这些单位用于不同的目的。

实时值 (real time values)，通常以毫秒或微秒指定，是应用程序代码的默认时间呈现方式。
它们具有普遍可移植和广泛理解的优点，尽管它们可能无法完美匹配底层硬件的精度。

内核通过 :c:func:`k_cycle_get_32` 和 :c:func:`k_cycle_get_64` API 呈现"周期" (cycle) 计数。
其目的是该计数器代表操作系统能够呈现给用户的最快周期计数器（例如，CPU 周期计数器），
并且读取操作非常快。期望是非常敏感的应用程序代码可能以轮询方式使用它来实现最大精度。
该计数器的频率需要随时间保持稳定，并可从 :c:func:`sys_clock_hw_cycles_per_sec` 获得
（在几乎所有平台上，这是一个运行时常量，计算结果为 CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC）。

对于异步计时，内核定义了"滴答" (ticks) 概念。"滴答"是内核执行所有内部运行时间和超时记账的内部计数。
期望在滴答边界上传递中断（在实际情况下尽可能），并且不跟踪分数滴答。
滴答率的选择可通过 :kconfig:option:`CONFIG_SYS_CLOCK_TICKS_PER_SEC` 配置。
大多数硬件平台（支持设置任意中断超时的平台）的默认值预期在 10 kHz 范围内，
软件仿真平台和传统驱动程序使用更传统的 100 Hz 值。

转换
----

Zephyr 为所有时间单位提供了一个详尽枚举的转换库，具有舍入控制。
任何"ms"（毫秒）、"us"（微秒）、"tick"或"cyc"单位都可以转换为任何其他单位。
提供舍入控制，每个转换都有"floor"（向下舍入到最接近的输出单位）、"ceil"（向上舍入）
和"near"（舍入到最接近）可用。最后，输出精度可以指定为 32 位或 64 位。

例如：:c:func:`k_ms_to_ticks_ceil32` 将毫秒输入值转换为下一个更高的滴答数，
返回截断为 32 位精度的结果；:c:func:`k_cyc_to_us_floor64` 将测量的周期计数转换为
经过的微秒数，以完整的 64 位精度表示。有关转换例程的完整枚举，请参阅参考文档。

在大多数平台上，其中各种计数器速率是彼此的整数倍，并且输出适合单个字，
这些转换扩展为 2-4 个操作序列，仅在实际需要和请求时才需要完整精度。

.. _kernel_timing_uptime:

运行时间
========

内核代表应用程序跟踪系统运行时间计数。这可以通过 :c:func:`k_uptime_get` 随时获得，
它提供自系统启动以来以毫秒为单位的运行时间值。这预期是大多数可移植应用程序代码使用的实用程序。

然而，内部跟踪是作为滴答的 64 位整数计数。具有精确时间要求的应用程序
（愿意进行自己的转换到可移植实时单位）可以通过 :c:func:`k_uptime_ticks` 访问此值。

超时
====

Zephyr 内核提供了许多带有"超时" (timeout) 参数的 API。从概念上讲，这表示事件将发生的时间。
例如：

* 内核阻塞操作，如 :c:func:`k_sem_take` 或 :c:func:`k_queue_get`，
  可以提供超时，如果没有数据可用，例程将在该超时后返回错误代码。

* 内核 :c:struct:`k_timer` 对象必须指定其持续时间和周期的延迟。

* 内核 :c:struct:`k_work_delayable` API 提供超时参数，指示何时将工作队列项添加到系统队列。

所有这些值都使用 :c:type:`k_timeout_t` 值指定。这是一个不透明的结构类型，
必须使用内核超时宏系列之一进行初始化。最常见的 :c:macro:`K_MSEC` 定义当前时间之后的毫秒时间。

相对超时的"当前时间"的含义取决于上下文：

* 当从超时回调中调度相对超时时（例如，从传递给 :c:func:`k_timer_init` 的到期函数
  或传递给 :c:func:`k_work_init_delayable` 的工作处理程序中），"当前时间"是当前触发超时
  最初调度的确切时间，即使"实时"已经前进。这是为了确保从另一个定时器的回调中调度的定时器
  将始终以与触发定时器的精确偏移量计算。因此可以以固定间隔触发，而不会随时间引入系统时钟漂移。

* 当从应用程序上下文调度超时时，"当前时间"是指内核接收超时值时 :c:func:`k_uptime_ticks`
  返回的值。

超时初始化的其他选项遵循上述单位约定：:c:macro:`K_NSEC()`、:c:macro:`K_USEC`、
:c:macro:`K_TICKS` 和 :c:macro:`K_CYC()` 分别指定将在指定的纳秒、微秒、滴答和周期数后到期的超时值。

:c:type:`k_timeout_t` 值的精度是可配置的，默认为 32 位。非滴答单位中的大运行时间计数
将经历复杂的翻转语义，因此预期具有长运行时间的时间敏感应用程序将配置为使用 64 位超时类型。

最后，可以将超时指定为自系统启动以来的绝对时间。使用 :c:macro:`K_TIMEOUT_ABS_MS`
初始化的超时指示将在系统运行时间达到指定值后到期的超时。
此 API 还有纳秒、微秒、周期和滴答变体。

时间管理内部机制
================

超时队列
--------

使用上述 API 指定的所有 Zephyr :c:type:`k_timeout_t` 事件都在单个全局事件队列中管理。
每个事件存储在双向链表中，伴随着来自前一个事件的以滴答为单位的增量计数。
要对事件采取的操作被指定为请求事件的子系统提供的回调函数指针，
以及预期嵌入在子系统定义的数据结构中的 :c:struct:`_timeout` 跟踪结构
（例如：:c:struct:`wait_q` 结构或 :c:type:`k_tid_t` 线程结构）。

请注意，通过 :c:type:`k_timeout_t` 传递的所有变体单位一旦插入列表就会转换为滴答。
内核内部没有多次转换步骤，因此无论存在多少事件或超时可能多长，精度都保证在滴答级别。

请注意，列表结构意味着管理大量超时所涉及的 CPU 工作在活动超时数中是二次的。
超时队列的 API 设计旨在允许更可扩展的后端数据结构，但目前不存在此类实现。

定时器驱动程序
-------------

滴答级别的内核时间由具有相对简单 API 的定时器驱动程序驱动。

* 驱动程序应该能够通过 :c:func:`sys_clock_announce` 调用向内核"宣布"新的滴答，
  该调用传递自上次宣布调用（或系统启动）以来经过的滴答的整数数量。
  这些调用可以在任何时候发生，但驱动程序应该尝试确保（在中断延迟交互的实际范围内）
  它们发生在滴答边界附近（即不是"在滴答中间"），最重要的是它们随时间正确，
  相对于其他计数器和现实世界时间的偏差最小。

* 驱动程序应该向内核提供 :c:func:`sys_clock_set_timeout` 调用，
  该调用指示在内核必须接收宣布调用以触发注册的超时之前可以经过多少滴答。
  在该时刻之前宣布新滴答是合法的（尽管它们必须是正确的），但之后的延迟将导致错过事件。
  请注意，此处传递的超时值是距当前时间的增量，但这并不免除驱动程序随时间提供稳定速率的滴答的要求。
  此函数的朴素实现容易出现分数滴答被错误"重置"并导致时钟偏差的错误。

* 驱动程序应该提供 :c:func:`sys_clock_elapsed` 调用，该调用提供自上次调用
  :c:func:`sys_clock_announce` 以来已经过了多少滴答（与现实世界时钟相比）的当前指示，
  内核需要测试新到达的超时是否到期。

请注意，此 API 的自然实现会产生"无滴答" (tickless) 内核，它仅接收和处理注册事件的定时器中断，
依赖可编程硬件计数器提供不规则的中断。但也可以轻松实现传统的"有滴答" (ticked) 或"哑"计数器驱动程序：

* 驱动程序可以以对应于 OS 滴答率的固定速率接收中断，每次调用 :c:func:`sys_clock_announce`，参数为 1。

* 驱动程序可以忽略对 :c:func:`sys_clock_set_timeout` 的调用，因为无论超时状态如何，
  每个滴答都将被宣布。

* 驱动程序可以为每次对 :c:func:`sys_clock_elapsed` 的调用返回零，
  因为不能检测到超过一个滴答已经过（因为否则会接收到中断）。

SMP 详细信息
-----------

一般来说，在多处理器上下文中运行时，上述定时器 API 不会改变。内核将在内部适当地同步所有访问，
并确保所有关键部分都很小且最小。但有些注意事项很重要：

* Zephyr 对哪个 CPU 服务定时器中断不可知。让每个定时器中断都在单个处理器上处理并非非法
  （尽管在某些情况下可能不太理想）。现有的 SMP 架构实现对称定时器驱动程序。

* :c:func:`sys_clock_announce` 调用预期在驱动程序级别进行全局同步。
  内核不进行任何按 CPU 跟踪，并期望如果两个定时器中断几乎同时触发，
  只有一个会向时间管理子系统提供当前滴答计数。另一个可以合法地提供滴答计数为零（如果没有滴答经过）。
  它不应该因为时间分片要求而"跳过"宣布调用（见下文）。

* 某些 SMP 硬件使用单个全局定时器设备，其他使用按 CPU 计数器。
  此处的复杂性（例如：确保 CPU 之间的计数器同步）预期由驱动程序管理，而不是内核。

* 通过 :c:func:`sys_clock_set_timeout` 传回驱动程序的下一个超时值对每个 CPU 都是相同的。
  因此，默认情况下，每个 CPU 将看到每个事件的同时定时器中断，即使根据定义只有一个应该看到
  :c:func:`sys_clock_announce` 的非零滴答参数。这对于时间敏感的应用程序可能是正确的默认值
  （因为它最小化了错误的 ISR 或中断锁定延迟超时的机会），但在某些情况下可能是性能问题。
  当前设计期望任何此类优化都是定时器驱动程序的责任。

时间分片
--------

时间管理子系统的辅助工作是向调度器提供滴答计数器，以允许实现线程的时间分片。
线程时间片不能是超时值，因为它不反映全局到期，而是反映需要在 SMP 上下文中
在每个 CPU 上独立跟踪的按 CPU 值。

因为可能没有其他硬件可用于驱动时间分片，Zephyr 复用现有的定时器驱动程序。
这意味着传递给 :c:func:`sys_clock_set_timeout` 的值可能会被钳位为小于当前下一个超时的值，
当时间分片线程当前被调度时。

保持毫秒 API 的子系统
--------------------

一般来说，这样的代码将像应用程序代码一样移植。来自用户的毫秒值可以按子系统喜欢的任何方式处理，
然后在向内核呈现时使用 :c:macro:`K_MSEC()` 转换为内核超时。

显然，这是以无法使用新功能为代价的，例如更高精度的超时构造函数或绝对超时。
但对于许多需求简单的子系统来说，这可能是可以接受的。

一个复杂性是 :c:macro:`K_FOREVER`。过去可能能够接受此值到其毫秒 API 的子系统不再可以，
因为它不再是整数类型。此类代码将需要使用不同的整数值令牌来表示"永远"。
:c:macro:`K_NO_WAIT` 当然也有同样的类型安全问题，但由于它是（并且一直是）简单的数字零，
它有一个自然的移植路径。

使用 ``k_timeout_t`` 的子系统
----------------------------

理想情况下，采用指定等待时间的"超时"参数的代码应尽可能使用内核本机抽象。
但 :c:type:`k_timeout_t` 是不透明的，需要在应用程序检查之前进行转换。

一些转换很简单。需要测试 :c:macro:`K_FOREVER` 的代码可以简单地使用 :c:macro:`K_TIMEOUT_EQ()`
宏来测试不透明结构的相等性并采取特殊操作。

更复杂的情况是当子系统需要获取超时并循环，等待它完成，同时执行一些可能需要对底层内核代码
进行多次阻塞操作的处理。例如，考虑这个设计：

.. code-block:: c

    void my_wait_for_event(struct my_subsys *obj, int32_t timeout_in_ms)
    {
        while (true) {
            uint32_t start = k_uptime_get_32();

            if (is_event_complete(obj)) {
                return;
            }

            /* 等待状态更改通知 */
            k_sem_take(obj->sem, timeout_in_ms);

            /* 减去经过的时间 */
            timeout_in_ms -= (k_uptime_get_32() - start);
        }
    }

此代码需要检查超时值，这不再可能。对于这种情况，新 API 提供内部
:c:func:`sys_timepoint_calc` 和 :c:func:`sys_timepoint_timeout` 例程，
将任意超时转换为基于其将到期的运行时间滴答的时间点值。因此，这样的循环可能如下所示：

.. code-block:: c

    void my_wait_for_event(struct my_subsys *obj, k_timeout_t timeout)
    {
        /* 从超时计算结束时间 */
        k_timepoint_t end = sys_timepoint_calc(timeout);

        do {
            if (is_event_complete(obj)) {
                return;
            }

            /* 使用剩余时间更新超时 */
            timeout = sys_timepoint_timeout(end);

            /* 等待状态更改通知 */
            k_sem_take(obj->sem, timeout);
        } while (!K_TIMEOUT_EQ(timeout, K_NO_WAIT));
    }

请注意，:c:func:`sys_timepoint_calc` 接受特殊值 :c:macro:`K_FOREVER` 和 :c:macro:`K_NO_WAIT`，
并且对绝对超时和常规超时的工作方式相同。相反，如果使用这些值创建时间点，
:c:func:`sys_timepoint_timeout` 可能返回 :c:macro:`K_FOREVER` 或 :c:macro:`K_NO_WAIT`，
如果时间点现在已过，也会返回后者。对于简单情况，也可以使用 :c:func:`sys_timepoint_expired`。

但对于使用这些的子系统仍需要一些注意。请注意，增量超时需要相对于"当前时间"进行解释，
显然该时间是调用 :c:func:`sys_timepoint_calc` 的时间。但用户期望时间是他们将超时传递给您的时间。
必须注意只调用此函数一次，尽可能与用户代码中的超时创建同步。它不应该用于"存储的"超时值，
并且永远不应该在循环中迭代调用。
