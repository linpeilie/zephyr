工作队列线程
############

.. contents::
    :local:
    :depth: 1

:dfn:`工作队列` 是一个内核对象,它使用专用线程以先进先出方式处理工作项。每个
工作项通过调用工作项指定的函数来处理。工作队列通常由 ISR 或高优先级线程用于将
非紧急处理卸载到低优先级线程,以便不影响时间敏感的处理。

可以定义任意数量的工作队列(仅受可用 RAM 限制)。每个工作队列由其内存地址引用。

工作队列具有以下关键属性:

* 已添加但尚未处理的工作项的**队列**。

* 处理队列中工作项的**线程**。线程的优先级是可配置的,允许它根据需要是协作式
  或抢占式。

无论工作队列线程优先级如何,工作队列线程都会在每个提交的工作项之间让步,以防止
协作式工作队列饿死其他线程。

工作队列在使用之前必须初始化。这会将其队列设置为空并生成工作队列的线程。线程
永远运行,但在没有工作项可用时休眠。

.. note::
   此处描述的行为与 Zephyr 2.6 版本之前使用的工作队列实现有所不同。其中包括:

   * 精确跟踪已取消工作项的状态,因此调用者无需担心取消返回时项可能正在处理。
     仍需要检查取消的返回值。
   * 直接将可延迟工作项提交到队列,使用 :c:macro:`K_NO_WAIT` 而不是总是通过
     超时 API,这可能会引入延迟。
   * 能够等待工作项完成或队列已排空。
   * 在调度可延迟工作项时更精细地控制行为,特别是允许在再次调度工作项时保持
     先前的截止日期不变。
   * 当项在另一个工作队列上处理时安全处理工作项重新提交。

   应避免使用 :c:func:`k_work_busy_get()` 或 :c:func:`k_work_is_pending()`
   的返回值,或测量可延迟工作计划前的剩余时间,以防止先前实现中观察到的竞争
   条件类型。另请参阅 `工作队列最佳实践`_。

工作项生命周期
**************

可以定义任意数量的**工作项**。每个工作项由其内存地址引用。

工作项分配有**处理程序函数**,这是工作队列的线程在处理工作项时执行的函数。此
函数接受单个参数,即工作项本身的地址。工作项还维护有关其状态的信息。

工作项在使用之前必须初始化。这会记录工作项的处理程序函数并将其标记为非挂起。

ISR 或线程可以通过将工作项提交到工作队列来**排队** (:c:enumerator:`K_WORK_QUEUED`)
工作项。提交工作项会将工作项追加到工作队列的队列。一旦工作队列的线程处理完队列中
所有前面的工作项,线程将从队列中删除下一个工作项并调用工作项的处理程序函数。根据
工作队列线程的调度优先级以及队列中其他项所需的工作,排队的工作项可能很快被处理,
也可能在队列中保留很长时间。

可延迟工作项可以**调度** (:c:enumerator:`K_WORK_DELAYED`) 到工作队列;
请参阅 `可延迟工作`_。

工作项在工作队列上运行时将**运行** (:c:enumerator:`K_WORK_RUNNING`),
如果它在线程请求取消之前开始运行,还可能**正在取消**
(:c:enumerator:`K_WORK_CANCELING`)。

工作项可以处于多种状态;例如,它可以:

* 在队列上运行;
* 标记为正在取消(因为线程使用 :c:func:`k_work_cancel_sync()` 等待工作项完成);
* 排队在同一队列上再次运行;
* 计划提交到(可能不同的)队列

*全部同时*。处于这些状态中任何一种的工作项是**挂起**
(:c:func:`k_work_is_pending()`)或**忙碌** (:c:func:`k_work_busy_get()`)。

处理程序函数可以使用线程可用的任何内核 API。但是,必须小心使用可能阻塞的操作
(例如获取信号量),因为在处理程序函数完成执行之前,工作队列无法处理队列中的
后续工作项。

如果不需要,可以忽略传递给处理程序函数的单个参数。如果处理程序函数需要有关
要执行的工作的其他信息,则可以将工作项嵌入到更大的数据结构中。然后,处理程序
函数可以使用参数值通过 :c:macro:`CONTAINER_OF` 计算封闭数据结构的地址,
从而获得对其所需的其他信息的访问权。

工作项通常初始化一次,然后在需要执行工作时提交到特定工作队列。如果 ISR 或线程
尝试提交已排队的工作项,则工作项不受影响;工作项保留在工作队列队列中的当前位置,
工作仅执行一次。

允许处理程序函数将其工作项参数重新提交到工作队列,因为此时工作项不再排队。
这允许处理程序分阶段执行工作,而不会过度延迟工作队列队列中其他工作项的处理。

.. important::
    挂起的工作项在项被工作队列线程处理之前*不得*更改。这意味着工作项在忙碌时
    不得重新初始化。此外,工作项的处理程序函数执行其工作所需的任何其他信息在
    处理程序函数完成执行之前不得更改。

可延迟工作
**********

ISR 或线程可能需要调度仅在指定时间段后处理的工作项,而不是立即处理。这可以通过
**调度****可延迟工作项**在未来时间提交到工作队列来完成。

可延迟工作项包含标准工作项,但添加了记录何时何地应提交项的字段。

可延迟工作项以类似于标准工作项的方式初始化并调度到工作队列,尽管使用不同的
内核 API。当发出调度请求时,内核启动超时机制,该机制在指定延迟已过后触发。
一旦超时发生,内核将工作项提交到指定的工作队列,它在那里保持排队,直到以标准
方式处理。

请注意,用于可延迟的工作处理程序仍然接收指向底层不可延迟工作结构的指针,
该指针无法从 :c:struct:`k_work_delayable` 公开访问。要访问包含可延迟工作
对象的对象,请使用此习惯用法:

.. code-block:: c

   static void work_handler(struct k_work *work)
   {
           struct k_work_delayable *dwork = k_work_delayable_from_work(work);
           struct work_context *ctx = CONTAINER_OF(dwork, struct work_context,
	                                           timed_work);
           ...


触发工作
********

:c:func:`k_work_poll_submit` 接口响应**轮询事件**(参见 :ref:`polling_v2`)
调度触发工作项,当监视的资源变得可用或引发轮询信号,或发生超时时,将调用用户
定义的函数。与 :c:func:`k_poll` 相比,触发工作不需要专用线程等待或主动轮询
轮询事件。

触发工作项是标准工作项,具有以下附加属性:

* 指向将触发工作项提交到工作队列的轮询事件数组的指针

* 包含轮询事件的数组的大小。

触发工作项以类似于标准工作项的方式初始化并提交到工作队列,尽管使用专用内核 API。
当发出提交请求时,内核开始观察轮询事件指定的内核对象。一旦至少一个观察到的内核
对象的状态发生变化,工作项就会提交到指定的工作队列,它在那里保持排队,直到以
标准方式处理。

.. important::
    触发工作项以及引用的轮询事件数组必须对完整的触发工作项生命周期(从提交到
    工作项执行或取消)有效且不能修改。

ISR 或线程可以**取消**它提交的触发工作项,只要它仍在等待轮询事件。在这种情况下,
内核停止等待附加的轮询事件,并且不执行指定的工作。否则无法执行取消。

系统工作队列
************

内核定义了一个称为*系统工作队列*的工作队列,它可供任何需要工作队列支持的应用
程序或内核代码使用。系统工作队列是可选的,仅在应用程序使用它时才存在。

.. important::
    只有在无法将新工作项提交到系统工作队列时,才应定义其他工作队列,因为每个
    新工作队列都会在内存占用中产生显著成本。如果新工作项无法与现有系统工作队列
    工作项共存而不产生不可接受的影响,则可以证明新工作队列是合理的;例如,如果
    新工作项执行阻塞操作,这会将其他系统工作队列处理延迟到不可接受的程度。

如何使用工作队列
****************

定义和控制工作队列
==================

使用类型 :c:struct:`k_work_q` 的变量定义工作队列。通过定义其线程使用的栈区域,
初始化 :c:struct:`k_work_q`(通过将其内存清零或调用 :c:func:`k_work_queue_init`),
然后调用 :c:func:`k_work_queue_start` 来初始化工作队列。栈区域必须使用
:c:macro:`K_THREAD_STACK_DEFINE` 定义,以确保在内存中正确设置。

以下代码定义并初始化工作队列:

.. code-block:: c

    #define MY_STACK_SIZE 512
    #define MY_PRIORITY 5

    K_THREAD_STACK_DEFINE(my_stack_area, MY_STACK_SIZE);

    struct k_work_q my_work_q;

    k_work_queue_init(&my_work_q);

    k_work_queue_start(&my_work_q, my_stack_area,
                       K_THREAD_STACK_SIZEOF(my_stack_area), MY_PRIORITY,
		       NULL);

此外,队列标识和与线程重新调度相关的某些行为可以由可选的最终参数控制;
有关详细信息,请参阅 :c:func:`k_work_queue_start()`。

以下 API 可用于与工作队列交互:

* :c:func:`k_work_queue_drain()` 可用于阻塞调用者,直到工作队列没有剩余项。
  从工作队列线程重新提交的工作项在队列正在排空时被接受,但来自任何其他线程或
  ISR 的工作项被拒绝。对提交更多工作的限制可以延伸到排空操作完成之后,以允许
  阻塞线程在队列"阻塞"时执行其他工作。请注意,排空队列对调度或处理可延迟项
  没有影响,但如果队列被阻塞且截止日期到期,项将静默无法提交。
* :c:func:`k_work_queue_unplug()` 删除由于先前排空操作而对队列提交的任何
  先前阻止。

提交工作项
==========

使用类型 :c:struct:`k_work` 的变量定义工作项。必须通过调用 :c:func:`k_work_init`
初始化它,除非使用 :c:macro:`K_WORK_DEFINE` 定义它,在这种情况下,初始化在
编译时执行。

可以通过调用 :c:func:`k_work_submit` 将初始化的工作项提交到系统工作队列,
或通过调用 :c:func:`k_work_submit_to_queue` 提交到指定的工作队列。

以下代码演示 ISR 如何将错误消息的打印卸载到系统工作队列。请注意,如果 ISR
在工作项仍排队时尝试重新提交工作项,则工作项保持不变,并且不会打印相关的错误
消息。

.. code-block:: c

    struct device_info {
        struct k_work work;
        char name[16]
    } my_device;

    void my_isr(void *arg)
    {
        ...
        if (error detected) {
            k_work_submit(&my_device.work);
	}
	...
    }

    void print_error(struct k_work *item)
    {
        struct device_info *the_device =
            CONTAINER_OF(item, struct device_info, work);
        printk("Got error on device %s\n", the_device->name);
    }

    /* 为设备初始化名称信息 */
    strcpy(my_device.name, "FOO_dev");

    /* 初始化用于打印设备错误消息的工作项 */
    k_work_init(&my_device.work, print_error);

    /* 将 my_isr() 安装为设备的中断处理程序(未显示) */
    ...


以下 API 可用于检查工作项的状态或与工作项同步:

* :c:func:`k_work_busy_get()` 返回指示工作项状态的标志快照。零值表示工作未
  调度、提交、正在执行或仍被工作队列基础设施引用。
* :c:func:`k_work_is_pending()` 是一个助手,仅当工作已调度、排队或运行时才
  指示 ``true``。
* :c:func:`k_work_flush()` 可以从线程调用以阻塞,直到工作项完成。如果工作
  未挂起,它会立即返回。
* :c:func:`k_work_cancel()` 尝试阻止工作项执行。这可能成功也可能不成功。
  从 ISR 调用是安全的。
* :c:func:`k_work_cancel_sync()` 可以从线程调用以阻塞,直到工作完成;如果
  取消成功或不必要(工作未提交或运行),它将立即返回。这可以在调用
  :c:func:`k_work_cancel()`(从 ISR)后使用,以确认 ISR 启动的取消完成。

调度可延迟工作项
================

使用类型 :c:struct:`k_work_delayable` 的变量定义可延迟工作项。必须通过调用
:c:func:`k_work_init_delayable` 初始化它。

对于延迟工作,有两种常见的用例,取决于如果发生新事件是否应延长截止日期。一个
例子是收集异步传入的数据,例如来自与键盘相关的 UART 的字符。有两个在延迟后
提交工作的 API:

* :c:func:`k_work_schedule()`(或 :c:func:`k_work_schedule_for_queue()`)
  将工作调度为在特定时间或延迟后执行。在延迟完成之前使用此 API 进一步尝试
  调度同一项将不会更改项将提交到其队列的时间。如果策略是继续收集数据,直到
  自**第一个**未处理数据接收以来指定的延迟,请使用此方法;
* :c:func:`k_work_reschedule()`(或 :c:func:`k_work_reschedule_for_queue()`)
  无条件设置工作的截止日期,替换任何先前的未完成延迟,并在必要时更改目标队列。
  如果策略是继续收集数据,直到自**最后一个**未处理数据接收以来指定的延迟,
  请使用此方法。

如果工作项未调度,两个 API 的行为相同。如果将 :c:macro:`K_NO_WAIT` 指定为
延迟,则行为就像项立即直接提交到目标队列,而无需等待最小超时(除非使用
:c:func:`k_work_schedule()` 且先前的延迟尚未完成)。

两者还具有允许控制用于提交的队列的变体。

辅助函数 :c:func:`k_work_delayable_from_work()` 可用于从传递给工作处理程序
函数的 :c:struct:`k_work` 指针获取包含 :c:struct:`k_work_delayable` 的指针。

以下附加 API 可用于检查工作项的状态或与工作项同步:

* :c:func:`k_work_delayable_busy_get()` 是可延迟工作的
  :c:func:`k_work_busy_get()` 的类似物。
* :c:func:`k_work_delayable_is_pending()` 是可延迟工作的
  :c:func:`k_work_is_pending()` 的类似物。
* :c:func:`k_work_flush_delayable()` 是可延迟工作的 :c:func:`k_work_flush()`
  的类似物。
* :c:func:`k_work_cancel_delayable()` 是可延迟工作的 :c:func:`k_work_cancel()`
  的类似物;与 :c:func:`k_work_cancel_delayable_sync()` 类似。

与工作项同步
============

虽然可以使用 :c:func:`k_work_busy_get()` 和
:c:func:`k_work_delayable_busy_get()` 从任何上下文确定常规和可延迟工作项的
状态,但某些用例需要在提交工作项后与工作项同步。:c:func:`k_work_flush()`、
:c:func:`k_work_cancel_sync()` 和 :c:func:`k_work_cancel_delayable_sync()`
可以从线程上下文调用,以等待直到达到请求的状态。

这些 API 必须提供一个 :c:struct:`k_work_sync` 对象,该对象没有应用程序可检查
的组件,但需要提供同步对象。如果代码预期在具有
:kconfig:option:`CONFIG_KERNEL_COHERENCE` 的架构上工作,则这些对象不应在栈上
分配。

工作队列最佳实践
****************

避免竞争条件
============

有时工作项必须处理的数据是天然线程安全的,例如当它由某个线程放入
:c:struct:`k_queue` 并在工作线程中处理时。更常见的是,需要外部同步来避免数据
竞争:工作线程可能检查或操作正在被另一个线程或中断访问的共享状态的情况。这种
状态可能是指示需要完成工作的标志,或者是由 ISR 或线程填充并由工作处理程序
读取的共享对象。

对于简单标志,:ref:`atomic_v2` 可能就足够了。在其他情况下,可以使用自旋锁
(:c:struct:`k_spinlock`)或线程感知锁(:c:struct:`k_sem`、:c:struct:`k_mutex`等)
来确保不会发生数据竞争。

如果所选的锁机制可以 :ref:`api_term_sleep`,那么允许工作线程休眠将饿死其他
工作队列项,这些项可能需要取得进展才能释放锁。工作处理程序应尝试使用其无等待
路径获取锁。例如:

.. code-block:: c

   static void work_handler(struct work *work)
   {
           struct work_context *parent = CONTAINER_OF(work, struct work_context,
	                                              work_item);

           if (k_mutex_lock(&parent->lock, K_NO_WAIT) != 0) {
                   /* 注意:如果工作项正在被取消,提交将失败。 */
                   (void)k_work_submit(work);
		   return;
	   }

	   /* 在锁下执行操作 */
	   k_mutex_unlock(&parent->lock);
	   /* 在无锁情况下执行操作 */
   }

请注意,如果锁由优先级低于工作队列的线程持有,则重新提交可能会饿死将释放锁的
线程,导致应用程序失败。在需要上述习惯用法的情况下,最好使用可延迟工作项,
并且应使用非零延迟(重新)调度工作,以允许持有锁的线程取得进展。

请注意,如果工作项已被取消,则从工作处理程序提交可能会失败。通常这是可以接受的,
因为一旦处理程序完成,取消将完成。如果不是,上面的代码必须采取其他步骤通知
应用程序无法执行工作。

隔离的工作项是自锁定的,因此您不需要持有外部锁来提交或调度它们。即使您使用
受此类锁保护的外部状态来防止进一步重新提交,只要您确定项最终将获取其锁并检查
该状态以确定是否应执行任何操作,重新提交是安全的。当由于无法获取锁而在其处理
程序中重新调度可延迟工作项时,需要某些其他自锁定状态(例如应用程序/驱动程序
在启动取消时设置的原子标志)来检测取消并避免在截止日期后再次提交已取消的工作项。

检查返回值
==========

所有工作 API 函数都返回底层操作的状态,在许多情况下,验证获得了预期结果很重要。

* 提交工作项(:c:func:`k_work_submit_to_queue`)可能会失败,如果工作正在被
  取消或队列不接受新项。如果发生这种情况,工作将不会执行,这可能导致由工作
  处理程序活动驱动的子系统变得无响应。
* 异步取消(:c:func:`k_work_cancel` 或 :c:func:`k_work_cancel_delayable`)
  可以在工作项仍由处理程序运行时完成。继续操作与工作处理程序共享的状态将
  导致可能导致故障的数据竞争。

许多竞争条件已经存在于 Zephyr 代码中,因为未检查操作的结果。

可能有充分的理由认为,指示操作未按预期完成的返回值不是问题。在这些情况下,
代码应该清楚地记录这一点,方法是(1)将返回值强制转换为 ``void`` 以指示有意
忽略结果,以及(2)记录在意外情况下会发生什么。例如:

.. code-block:: c

   /* 如果失败,工作处理程序将检查 pub->active 并退出而不传输。 */
   (void)k_work_cancel_delayable(&pub->timer);

但是,在这种情况下,以下代码仍必须避免数据竞争,因为它无法保证工作线程不会
访问与工作相关的状态。

不要过早优化
============

工作队列 API 设计为在从多个线程和中断调用时是安全的。尝试外部检查工作项的
状态并根据结果做出决策可能会产生新问题。

因此,当新工作到来时,只需提交它。不要尝试通过使用 :c:func:`k_work_is_pending`
或 :c:func:`k_work_busy_get()` 检查快照状态来检查工作项是否已提交,或通过
:c:func:`k_work_delayable_remaining_get()` 检查非零延迟来"优化"。这些检查
是脆弱的:"忙碌"指示在返回测试时可能已过时,"非忙碌"指示如果从多个上下文
提交工作,或(对于可延迟工作)如果截止日期已完成但工作仍处于排队或运行状态,
也可能是错误的。

一般最佳实践是始终在共享状态中维护可由处理程序检查以确认是否有工作要做的某些
条件。这样,您可以使用工作处理程序作为标准清理路径:您可以在工作处理程序本身
中完成所有操作,而不必在提交项的点处理取消和清理。

可以安全使用 :c:func:`k_work_is_pending` 的罕见情况是作为检查以避免调用
:c:func:`k_work_flush` 或 :c:func:`k_work_cancel_sync()`,如果您*确定*在
检查时没有其他人可能提交工作(通常是因为您持有阻止访问用于提交的状态的锁)。

建议用途
********

使用系统工作队列将复杂的中断相关处理从 ISR 延迟到共享线程。这允许及时完成
中断相关处理,而不会损害系统响应后续中断的能力,并且不需要应用程序定义和管理
其他线程来执行处理。
