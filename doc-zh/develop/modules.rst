.. _modules:

模块（外部项目）
###############

Zephyr 依赖于几个外部维护项目的源代码,以避免重复造轮子,并在有意义的地方尽可能多地重用
成熟的代码。在 Zephyr 构建系统的上下文中,这些称为*模块*。这些模块必须与 Zephyr 构建系统集成,
如本页其他部分所详细描述。

要被归类为候选者纳入默认模块列表,外部项目需要在 Zephyr 项目外有其自己的生命周期,
即驻留在其自己的存储库中,并有其自己的贡献和维护工作流以及发布流程。Zephyr 模块不应包含
专为 Zephyr 编写的代码。相反,此类代码应贡献到主 zephyr 树。

要包含在 Zephyr 项目的默认清单中的模块需要提供 TSC 支持和批准的功能或功能,并应遵守
:ref:`模块许可要求 <modules_licensing>` 和 :ref:`贡献指南 <modules_contributing>`。
它们还应该有一个 Zephyr 开发人员致力于维护模块代码库。

Zephyr 依赖于几类模块,包括但不限于:

- 调试器集成
- 硅供应商硬件抽象层 (HAL)
- 密码学库
- 文件系统
- 进程间通信 (IPC) 库

另外,在某些情况下,模块(特别是供应商 HAL)可以包含对可选的 :ref:`二进制 blob <bin-blobs>` 的引用。

此页面总结了一个政策和最佳实践列表,旨在更好地组织 Zephyr 模块中的工作流。

.. _modules-vs-projects:

模块 vs west 项目
*****************

本页面描述的 Zephyr 模块与 :ref:`west 项目 <west-workspace>` 不同。实际上,模块
:ref:`根本不需要 west <modules_without_west>`。但是,当使用 :ref:`west 的模块 <modules_using_west>`
时,构建系统使用 west 来查找模块。

总结:

- 模块是包含 :file:`zephyr/module.yml` 文件的存储库,以便 Zephyr 构建系统可以从存储库中拉取源代码。
- :ref:`West 项目 <west-manifests-projects>` 是 :file:`west.yml` 清单文件中 ``projects:`` 部分中的条目。
- West 项目通常也是模块,但不总是这样。有些 west 项目不包含在最终固件映像中(例如工具),
  因此不需要是模块。
- Zephyr 构建系统通过 :ref:`west 本身 <modules_using_west>` 或通过
  :ref:`ZEPHYR_MODULES CMake 变量 <modules_without_west>` 找到模块。

此页面的内容仅适用于模块,不适用于 west 项目一般(除非它们是模块本身)。

模块存储库
*********

* 默认清单中包含的所有模块应托管在 zephyrproject-rtos GitHub 组织下的存储库中。

* 模块存储库代码库应在存储库根目录的 :file:`zephyr/` 文件夹中包含 *module.yml* 文件。

* 模块存储库名称应遵循使用小写字母和破折号而不是下划线的约定。此规则将适用于所有新模块存储库,
  除了直接追踪外部项目(托管在 Git 存储库中)的存储库;此类模块可能以其外部项目对应物的名称命名。

  .. note::

     不符合上述约定的现有模块存储库不需要重命名以遵守上述约定。

* 模块存储库名称应在 :file:`zephyr/module.yml` 文件中显式设置。

* 模块应使用 "zephyr" 作为存储库主分支的默认名称。用于特定目的的分支,
  例如 LTS Zephyr 版本的模块分支,应具有以 'zephyr\_' 前缀开头的名称。

* 如果模块具有外部(上游)项目存储库,模块存储库应保持上游存储库文件夹结构。

  .. note::

     不需要在模块存储库中维护镜像外部存储库主分支的'master'分支。
     不推荐,因为这可能会围绕模块的主分支(应该是'zephyr')造成混淆。

* 模块应使用以模块名开头的 include 路径来公开所有提供的头文件。
  (例如,mcuboot 应将其 ``bootutil/bootutil.h`` 公开为 "mcuboot/bootutil/bootutil.h"。)

.. _modules_synchronization:

与上游同步
========

优选与相应外部项目的最新稳定版本同步模块存储库。但是,允许使用最新开发分支
尖端更新 Zephyr 模块存储库,如果这需要在模块代码库中获取重要更新。与上游同步模块时,
必须记录执行特定更新的基本原理。

允许实践的要求
-----------

对模块存储库主分支的更改,包括与上游代码库的同步,可能只能通过拉取请求应用。
这些拉取请求应*可由 Zephyr CI 验证*且*可合并*(例如,使用 Github UI 中的*Rebase 并合并*
或*创建合并提交*选项)。这确保传入的更改始终**可审查**,并且*下游*模块存储库历史是增量的
(即,现有提交、标签等始终被保留)。此政策还允许直接在要引入模块存储库的更改集上运行
Zephyr CI、git lint、identity 和许可证检查。

.. note::

     不允许强制推送到模块的主分支。

允许的实践
--------

以下实践符合上述要求,应在所有模块存储库中遵循。由模块代码所有者选择首选同步实践取决于它,
但需要在各个模块存储库中一致地遵循选定的实践。

**使用来自上游的差异更新模块:**
上游更改作为单个*快照*提交(手动差异)在针对模块主分支的拉取请求中,
可以使用*Rebase & merge* 操作合并。这种方法很简单,应该适用于所有模块,缺点是抑制了模块存储库中的上游历史。

  .. note::

     上述实践是仅在模块中允许的唯一实践,其中外部项目未托管在上游 Git 存储库中。

提交消息应该标识上游项目 URL、模块更新到的版本(上游版本、标签、提交 SHA,如适用等),
以及执行更新的原因。

**通过合并上游分支更新模块:**
上游更改通过执行预期上游分支(例如主分支、最新发布分支等)的 Git 合并来引入,
将结果提交给针对模块主分支的拉取请求,并使用*创建合并提交*操作合并拉取请求。
此方法适用于具有上游项目 Git 存储库的模块。这种方法的主要优点是上游存储库历史
(即原始提交 SHA)在模块存储库中得到保留。这种方法的缺点是在下游主分支中生成了两个额外的合并提交。

对 Zephyr 模块的贡献
*******************

.. _modules_contributing:

个人角色和责任
============

为便于管理 Zephyr 模块存储库,定义了以下个人角色。

**管理员:** 每个 Zephyr 模块应有一个管理员负责管理对模块存储库的访问,
例如,根据模块所有者的请求将个人添加为存储库中的协作者。模块管理员是
具有模块 GitHub 存储库管理员权限的项目成员组的成员。

**模块所有者:** 每个模块应有一个模块代码所有者。模块所有者对 Zephyr 模块存储库的内容有总体责任。
特别是,模块所有者将:

* 协调模块存储库中的代码审查
* 成为针对存储库主分支的拉取请求中的默认受理人
* 根据所有者的判断请求添加额外的协作者到存储库
* 定期将模块存储库与其上游同步
* 遵循 :ref:`modules_synchronization` 中描述的政策定期与其上游对应物同步
* 意识到外部项目中的安全漏洞问题,并更新模块存储库以包含安全修复,
  只要修复在上游代码库中可用
* 在 Zephyr 发布说明中列出存在于模块代码库中的任何已知安全漏洞问题。

  .. note::

     模块所有者不需要是 Zephyr :ref:`维护者 <project_roles>`。

**合并者:** Zephyr 发布工程团队有权和责任在模块存储库的主分支中合并已批准的拉取请求。

维护模块代码库
============

zephyr 主树中的更新,例如公共 Zephyr API 中的更新,可能需要修补模块的代码库。
保持模块代码库最新的责任在 zephyr 中此类更新的**贡献者**和模块**所有者**之间共享。
特别是:

* zephyr 中原始更改的贡献者需要提交模块存储库中所需的相应更改,以确保
  zephyr 拉取请求的 CI 以及模块集成测试成功。

* 模块所有者对与 zephyr 主树同步和测试模块代码库有总体责任。这包括除了
  Zephyr 的 CI 执行的测试之外,模块代码库的偶尔高级测试。模块所有者需要修复
  模块代码库中 Zephyr 拉取请求 CI 运行未捕获的问题。

.. _modules_changes:

对模块的贡献更改
===============

直接将更改提交和合并到模块的代码库,即在它们被合并到相应的外部项目存储库之前,
应仅限于:

* 由于 zephyr 主树中的更新所需的更改
* 不应该等待首先在外部项目中合并的紧急更改,例如对安全漏洞的修复。

对模块代码库的非平凡更改,包括模块设计或功能中的更改,如果模块具有上游项目存储库,
应该被劝阻。在这种情况下,此类更改应直接提交到上游项目。

:ref:`向模块提交更改 <submitting_new_modules>` 详细描述了对模块存储库进行贡献更改的流程。

贡献指南
------

对 Zephyr 模块的贡献应遵循一般项目 :ref:`贡献指南 <contribute_guidelines>`。

**拉取请求:** 可以以最少 2 个批准合并,包括 PR 受理人的批准。
除此之外,模块存储库中的拉取请求只能在通过 Zephyr CI 工具验证引入的更改时才能合并,
如本页其他部分所详细描述。

模块存储库主分支中拉取请求的合并必须与 zephyr 主树中相应的清单文件更新相耦合。

**问题报告:** GitHub 问题 在模块存储库中被意图禁用,支持集中式问题报告政策。
涉及例如模块中错误或增强的票证应在主 zephyr 存储库中打开。问题应使用相应的
GitHub 标签(如适用)进行标记,对应于每个模块。

  .. note::

     允许向 zephyr 模块提交错误报告以追踪 Zephyr 中对应的上游项目错误。
     这些错误报告不应影响 :ref:`发布质量标准 <release_quality_criteria>`。

.. _modules_licensing:

许可要求和政策
*************

模块代码库中的所有源文件应包含许可证头,除非模块存储库具有覆盖不包含许可证头的
源文件的**主许可证文件**。

主许可证文件应仅在 Zephyr 开发人员存在于外部项目中的情况下由其添加到模块的代码库中,
并且它们包含许可的 OSI 兼容许可证。主许可证文件应优选包含完整的许可证文本而不是
包含 SPDX 许可证标识符。如果存在多个主许可证文件,应该清楚哪个许可证适用于模块代码库中的每个源文件。

模块源文件中的单个许可证头优先于主许可证。

要添加到模块存储库中的任何新内容将需要有许可证覆盖。

  .. note::

     Zephyr 建议通过单个许可证头和主许可证文件传达模块许可。这不是硬性要求;
     如果外部项目有其自己的实践来传达许可如何在模块代码库中应用(例如,具有单个或多个主许可证文件),
     此实践可能被 Zephyr 模块接受并被引用,只要满足许可要求,例如 OSI 兼容性。

许可政策
======

创建模块存储库时,开发人员应:

* 导入主许可证文件(如果存在于外部项目中),并
* 记录(例如在模块 README 或 .yml 文件中)覆盖模块代码库的默认许可证。

许可证检查
--------

许可证检查(通过 CI 工具)应在添加新内容的模块存储库中的每个拉取请求上启用。

文档要求
*******

所有 Zephyr 模块存储库应包含一个 .rst 文件记录:

* 模块的范围和目的
* 模块如何与 Zephyr 集成
* 模块存储库的所有者
* 与外部项目的同步信息(提交、SHA、版本等)
* 许可信息,如 :ref:`modules_licensing` 中所述。

此文件对于模块的包含是必需的,并且包含的信息应保持最新。

测试要求
*******

所有 Zephyr 模块应提供某种程度的**集成**测试,确保与 Zephyr 的集成正确。
集成测试:

* 可能采用驻留在 zephyr 主树中的最小样本和测试集的形式
* 应验证与 Zephyr 集成的模块的基本用法(配置、功能 API 等)。
* 应在拉取请求中作为 twister 运行的一部分构建和执行(例如在 QEMU 中),
  这些拉取请求在模块存储库中引入更改。

  .. note::

     候选包含在 Zephyr 默认清单中的新模块应提供某种程度的集成测试。

  .. note::

     供应商 HAL 通过在目标平台上构建或执行的 Zephyr 测试进行隐式测试,
     因此不需要提供集成测试。

集成测试的目的不是提供模块的功能验证;这应该是外部项目测试框架的一部分。

某些外部项目提供驻留在上游测试基础设施中但明确为 Zephyr 编写的测试套件。
这些测试可能(但不是必需的)是 Zephyr 测试框架的一部分。

弃用和删除模块
*************

模块可能因以下原因被弃用,包括但不限于:

* 模块中缺乏维护
* 外部项目中的许可更改
* 代码库变为过时

模块信息应指示模块是否已弃用,构建系统应在尝试使用已弃用的模块构建 Zephyr 时发出警告。

已弃用的模块可以在 2 个 Zephyr 版本后从 Zephyr 默认清单中删除。

  .. note::

     已删除的模块的存储库应通过其原始 URL 保持可访问,
     因为旧的 Zephyr 版本需要它们。
