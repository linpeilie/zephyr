.. _api_lifecycle:

API 生命周期
#############

使用 Zephyr API 的开发人员需要知道他们可以信任给定 API 在未来版本中不会更改多长时间。同时,维护和扩展 Zephyr API 的开发人员需要能够引入尚未完全验证的新 API,并在旧 API 不再最优或底层平台不再支持时可能淘汰它们。


.. figure:: api_lifecycle.png
    :align: center
    :alt: API 生命周期
    :figclass: align-center

    API 生命周期

所有 API 及其成熟度级别的最新表格可在 :ref:`api_overview` 页面中找到。


.. _api_lifecycle_experimental:

实验性
*************

实验性 API 表示最近引入了一项功能,可能会在未来版本中更改或删除。请试用它并通过 `开发者邮件列表 <https://lists.zephyrproject.org/g/devel>`_ 向社区提供反馈。

以下要求适用于所有新 API:

- API 文档(用法)
  解释其设计和假设、如何使用、当前实现限制以及未来潜力(如果适用)。
- API 引入应伴随至少一个该 API 的实现(在外设 API 的情况下,这对应于一个驱动程序)
- 至少一个使用新 API 的示例(可能只在单个开发板上构建)

引入新的实验性 API 时,在定义 API 的头文件中标记 API 版本。实验性 API 的版本应为次版本号不超过一 (0.1.z)。(参见 :ref:`api_overview`)

外设 API(硬件相关)
==================================

为新外设或驱动程序子系统引入 API(带有文档的公共头文件)时,强制进行 API 审查,由来自不同供应商的代表组成的架构工作组推动。

当 API 在不同硬件平台上至少有两个实现时,应将其提升为 ``不稳定``。

.. _api_lifecycle_unstable:

不稳定
********

API 正在稳定中,但尚未经过足够的实际测试以被视为稳定。API 被认为是通用性质的,可以在不同的硬件平台上使用。

当 API 状态更改为不稳定 API 时,在定义 API 的头文件中标记 API 版本。不稳定 API 的版本应为次版本号大于一 (0.y.z | y > 1)。(参见 :ref:`api_overview`)

.. note::

   不会公布更改。

外设 API(硬件相关)
==================================

当 API 在不同硬件平台上至少有两个实现时,应从 ``实验性`` 提升到 ``不稳定``。

硬件无关 API
=======================

对于硬件无关 API,需要多个应用程序使用它才能将 API 从 ``实验性`` 提升到 ``不稳定``。

.. _api_lifecycle_stable:

稳定
*******

API 已被证明令人满意,但底层代码的清理可能会导致小的更改。如果合理,将保持向后兼容性。

满足以下要求后,可以将 API 声明为 ``稳定``:

- 新 API 的测试用例覆盖率达到 100%
- 代码中的完整文档。所有公共接口都应记录并在在线文档中提供。
- API 已被使用并且在至少 2 个开发版本中可用
- 稳定 API 可以随时获得向后兼容的更新、错误修复和安全修复

为了将 API 声明为 ``稳定``,需要遵循以下步骤:

#. 必须打开一个拉取请求,更改 :ref:`api_overview` 表中的相应条目
#. 必须向 ``devel`` 邮件列表发送一封电子邮件,宣布 API 升级请求
#. 必须将拉取请求提交到下一次 `Zephyr 架构会议`_ 进行讨论,如果没有异议,将合并拉取请求


当 API 状态更改为稳定 API 时,在定义 API 的头文件中标记 API 版本。稳定 API 的版本应为主版本号为一或更大 (x.y.z | x >= 1)。(参见 :ref:`api_overview`)

.. _breaking_api_changes:

引入破坏性 API 更改
================================

如上所述,稳定 API 在其生命周期中力求保持向后兼容。但是,在某些情况下,实现此目标会阻碍技术进步,或者在不对 API 及其实现的维护造成不合理负担的情况下根本不可行。

破坏性 API 更改定义为强制用户修改其现有代码以维护其应用程序当前行为的更改。应用程序的重新编译需求(无需更改应用程序本身)不被视为破坏性 API 更改。

为了限制和控制破坏向后兼容性承诺的更改的引入,当认为此类更改对于接受项目是必要的时,必须遵循以下步骤:

#. 必须在 GitHub 上打开一个 :ref:`RFC 问题 <rfcs>`,包含以下内容:

   .. code-block:: none

      标题:     RFC: 破坏性 API 更改: <子系统>
      内容:     - 问题描述:
                   - 有关为什么需要更改的背景信息
                 - 提议的更改(详细):
                   - API 更改的简要描述
                 - 详细 RFC:
                   - 函数调用更改
                   - 设备树更改(源和绑定)
                   - Kconfig 选项更改
                 - 依赖项:
                   - 对 API 用户的影响,包括使树外用户适应更改所需的步骤

   RFC 问题可以链接到包含代码形式的这些更改的拉取请求,而不是更改的书面描述。
#. RFC 问题必须用 GitHub ``Breaking API Change`` 标签标记
#. RFC 问题必须提交到下一次 `Zephyr 架构会议`_ 进行讨论
#. 必须向 ``devel`` 邮件列表发送一封电子邮件,主题与 RFC 问题标题相同,并链接到 RFC 问题

然后,RFC 将通过问题评论获得反馈,并将在 Zephyr 架构会议上讨论,利益相关者和社区将有机会详细讨论。

最后,如果未作为第一步的一部分完成,则必须在 GitHub 上打开拉取请求。由提议更改的人决定是同时引入 RFC 和拉取请求,还是等到 RFC 获得足够的共识,以便实现可以充满信心地进行并被接受。
拉取请求必须包括以下内容:

- 与 RFC 问题匹配的标题
- RFC 问题的链接
- 对 API 的实际更改

  - 对 API 头文件的更改
  - 对 API 实现的更改
  - 对相关 API 文档的更改
  - 对设备树源和绑定的更改

- 使树内 API 用户适应更改所需的更改。根据此任务的范围,这可能需要来自相应维护者的额外帮助
- 在下一个即将发布的版本的发布说明的"API 更改"部分中的条目
- 标签 ``API``、``Breaking API Change`` 和 ``Release Notes``,以及任何其他适用的标签
- 如果 RFC 尚未在 `Zephyr 架构会议`_ 中讨论和同意,则标签 ``Architecture Review``

完成上述步骤后,提案的结果将取决于相应子系统的维护者对实际拉取请求的批准。与任何其他拉取请求一样,作者可以请求在 `Zephyr TSC 会议`_ 中讨论它,甚至最终对其进行投票。

如果合并了拉取请求,则必须向 ``devel`` 和 ``user`` 邮件列表发送一封电子邮件,通知他们更改。

应更改 API 版本以表示向后不兼容的更改。这是通过递增主版本号 (X.y.z | X > 1) 来实现的。它也可能包括次版本号和修订版本号的更改。当主版本号递增时,修订版本号和次版本号必须重置为 0。(参见 :ref:`api_overview`)

.. note::

   破坏性 API 更改将在迁移指南中列出和描述。

已弃用
***********

.. note::

   不稳定 API 可以随时删除而无需弃用。
   API 的弃用和删除将在发布说明的"API 更改"部分中公布。

弃用现有 API 的要求如下:

- 弃用时间(稳定 API):2 个版本
  API 需要在至少两个完整版本中标记为已弃用。
  例如,如果 API 在版本 4.0 中首次弃用,
  则最早可以在 4.2 中删除。
  在特殊情况下,由架构工作组确定,
  API 可能更快弃用。
- 弃用时需要什么:

  - 标记为已弃用。这可以通过使用编译器本身(函数声明的 ``__deprecated`` 和宏定义的 ``__DEPRECATED_MACRO``)来完成,或者通过引入 Kconfig 选项(通常包含 ``DEPRECATED`` 字样)来完成,启用后,会将 API 恢复到其以前的形式
  - 记录弃用
  - 在下一个即将发布的版本的发布说明的"API 更改"中包含弃用
  - 使用已弃用 API 的代码需要修改以删除对该 API 的使用
  - 更改需要是原子的和可二分的
  - 在相应版本的 `GitHub 问题 <https://github.com/zephyrproject-rtos/zephyr/labels/deprecation_tracker>`_ 中添加一个条目,跟踪已弃用 API 的删除。
    在此示例中,是与 4.2 版本对应的问题。

在弃用等待期间,API 将处于 ``已弃用`` 状态。Zephyr 维护者将跟踪 ``docs.zephyrproject.org`` 上已弃用 API 的使用情况,并支持开发人员迁移其代码。Zephyr 将继续提供警告:

- API 文档将通知用户 API 已弃用。
- 在构建时尝试使用已弃用的 API 将向控制台记录警告。


已淘汰
*******

在此阶段,API 被删除。

目标删除日期是弃用公布后的 2 个版本。Zephyr 维护者将决定何时实际删除 API:这将取决于有多少开发人员已成功从已弃用的 API 迁移,以及 API 需要多紧急地删除。

如果可以删除 API,则将删除它。维护者将删除相应的文档,并以通常的方式传达删除:发布说明、邮件列表、Github 问题和拉取请求。

如果不能删除 API,维护者将继续支持迁移,并更新路线图,旨在在下一个版本中删除 API。
