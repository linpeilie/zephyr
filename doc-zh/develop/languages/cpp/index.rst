.. _language_cpp:

C++ 语言支持
####################

C++ 是一种基于 C 语言的通用面向对象编程语言。

启用 C++ 支持
********************

Zephyr 支持用 C 和 C++ 编写的应用程序。但是,要在应用程序中使用 C++,您必须通过在
应用程序配置文件中选择 :kconfig:option:`CONFIG_CPP` 来配置 Zephyr 以包含 C++ 支持。

要启用 C++ 支持,编译器工具链还必须包含 C++ 编译器,并且包含的编译器必须受 Zephyr
构建系统支持。:ref:`toolchain_zephyr_sdk`(包括 GNU C++ 编译器(GCC 的一部分))
受 Zephyr 支持,此处记录的功能及其可用性假定使用 Zephyr SDK。

Zephyr 应用程序的默认 C++ 标准级别(即编译器标志强制执行的语言)是 C++11。
其他标准可通过 kconfig 选择,例如 :kconfig:option:`CONFIG_STD_CPP98`。
Zephyr 支持和测试的最旧标准是 C++98。

编译源文件时,构建系统根据文件的后缀(扩展名)选择 C++ 编译器。
使用 **cpp** 或 **cxx** 后缀标识的文件使用 C++ 编译器编译。
例如,:file:`myCplusplusApp.cpp` 使用 C++ 编译。

C++ 标准要求 ``main()`` 函数具有 ``int`` 返回类型。您的 ``main()`` 必须定义为
``int main(void)`` 或 ``int main(int, char **)``。要使用带参数的 main,
必须选择 ``CONFIG_BOOTARGS`` 选项。Zephyr 忽略 main 的返回值,因此应用程序不应
返回状态信息,而应返回零。

.. note::
    不要将 C++ 用于内核、驱动程序或系统初始化代码。

语言特性
*****************

Zephyr 目前仅提供 C++ 功能的一个子集。以下功能 *不* 支持:

* 静态全局对象析构
* 操作系统特定的 C++ 标准库类(例如 ``std::thread``、``std::mutex``)

虽然不是详尽的列表,但支持以下功能:

* 继承
* 虚函数
* 虚表
* 静态全局对象构造函数
* 使用 **new** 和 **delete** 操作符的动态对象管理
* 异常
* :abbr:`RTTI (运行时类型信息)`
* 标准模板库(STL)

静态全局对象构造函数在驱动程序初始化之后但在应用程序 :c:func:`main()` 函数之前
初始化。因此,C++ 的使用仅限于应用程序代码。

为了使用 C++ 异常,必须在应用程序配置文件中选择 :kconfig:option:`CONFIG_CPP_EXCEPTIONS`。

Zephyr 最小 C++ 库
**************************

Zephyr 最小 C++ 库(:file:`lib/cpp/minimal`)提供 C++ 标准库和应用程序二进制接口(ABI)
函数的最小子集,以启用基本的 C++ 语言支持。这包括:

* ``new`` 和 ``delete`` 操作符
* 虚函数存根和虚表
* 全局构造函数的静态全局初始化器

最小 C++ 库的范围严格限于提供基本的 C++ 语言支持,它不实现任何`标准模板库(STL)`_
类和函数。因此,它仅适用于实现自己的(非标准)类库且不依赖标准模板库(STL)组件的
应用程序。

任何使用标准模板库(STL)组件(例如 ``std::string`` 和 ``std::vector``)的应用程序
都必须启用 C++ 标准库支持。

C++ 标准库
********************

`C++ 标准库`_ 是 ISO C++ 标准(``std`` 命名空间)的一部分的类和函数的集合。

Zephyr 不以源代码形式包含任何 C++ 标准库实现。相反,它允许配置构建系统以链接到
C++ 编译器工具链中包含的预构建 C++ 标准库。

要启用 C++ 标准库,请从应用程序配置文件中的
:kconfig:option:`CONFIG_LIBCPP_IMPLEMENTATION` 选择适用的特定于工具链的 C++
标准库类型。

例如,使用 :ref:`toolchain_zephyr_sdk` 构建时,可以通过在应用程序配置文件中选择
:kconfig:option:`CONFIG_GLIBCXX_LIBCPP` 来配置构建系统以链接到 GNU C++ 库
(``libstdc++.a``),这是一个功能齐全的 C++ 标准库,提供 ISO C++ 标准要求的所有功能,
包括标准模板库(STL)。

Zephyr 支持以下 C++ 标准库:

* GNU C++ 库(:kconfig:option:`CONFIG_GLIBCXX_LIBCPP`)
* ARC MetaWare C++ 库(:kconfig:option:`CONFIG_ARCMWDT_LIBCPP`)

需要完整 C++ 标准库功能的 Zephyr 子系统可以从其配置中选择
:kconfig:option:`CONFIG_REQUIRES_FULL_LIBCPP`,这会自动选择兼容的 C++ 标准库,
除非选择了特定 C++ 标准库的 Kconfig 符号。

头文件以及 C 和 C++ 之间的不兼容性
****************************************************

为了相互交互,C 和 C++ 必须通过头文件共享代码:数据结构、宏、静态函数等。
虽然 C 和 C++ 有很大的重叠,但它们是具有`已知不兼容性`_的不同语言。C 不仅仅是
C++ 的子集。标准级别(例如:"C++11")增加了另一层复杂性,因为新功能通常受到另一种
语言的启发并从中复制,但要晚很多年,并且有细微的差异。使事情更加复杂的是,
编译器通常在功能标准化之前提供功能的早期原型。标准可能存在不同编译器解释不同的
歧义。编译器可能存在错误,这些错误可能需要解决方法。为了解决这个问题,许多项目
将自己限制在有限数量的工具链中。Zephyr 没有这样做。

这些兼容性问题对头文件的影响尤为严重。不仅因为它们必须在 C 和 C++ 之间兼容,
还因为由于 *间接* 包含以及现实世界项目中典型的`缺乏结构和头文件组织`_,
它们最终会在令人惊讶的大量其他源文件中编译。因此,头文件暴露于更多种类的工具链和
项目配置中。增加更多约束,Zephyr 项目在代码风格、编译器警告、静态分析器和标准
合规性(例如:MISRA)方面有严格的策略。

综合起来,所有这些约束都会使编写头文件变得非常具有挑战性。本节的目的是记录一些
在 Zephyr 特定上下文中的最佳"头文件实践"和经验教训。虽然这里的很多信息不是
Zephyr 特定的,但本节不能替代 C/C++ 标准、教科书和其他参考资料的知识。

测试
-------

幸运的是,Zephyr 项目拥有广泛的测试和 CI 基础设施,提供覆盖率基线、及早发现问题、
强制执行策略并在一定程度上控制此类组合爆炸。``tests/lib/cpp/cxx/`` 在这种情况下
非常有用,因为它们的 ``testcase.yaml`` 配置让 ``twister`` 快速迭代一系列 ``-std``
参数:``-std=c++98``、``-std=c++11`` 等。

请记住,未使用的宏不会被编译。

指定初始化器
-----------------------

初始化宏在头文件中很常见,因为它们有助于减少样板代码。C99 添加了通过"指定"成员名称
而不是 *裸* 表达式列表来初始化 ``struct`` 和 ``union`` 类型的功能。一些 GCC 版本
即使在 C90 模式下也支持指定初始化器。

在简单级别使用时,指定初始化器不易出错、更易读且更灵活。另一方面,C99 允许一组
令人惊讶的大而宽松的可能性:指定初始化器可以乱序、重复、"嵌套"(``.a.x =``),
可以省略各种其他大括号,可以混合指定和非指定初始化器等。

二十年后,C++20 向 C++ 添加了指定初始化器,但方式更加受限;部分原因是 C++
``struct`` 实际上是一个 ``class``。如 C++ 提案编号 P0329(与 C 进行比较)或任何
完整的 C++ 参考中所述,不允许混合,初始化器必须按顺序排列(允许间隙)。

有趣的是,C++20 中的新限制可能导致 ``gcc -std=c++20`` 无法编译使用
``gcc -std=c++17`` 成功编译的代码。例如,``gcc -std=c++17`` 和更早版本允许
初始化器和裸表达式的 C 风格混合。使用 ``gcc -std=c++20`` *使用相同的 GCC 版本*
无法编译。

建议:为了最大化不同 C 和 C++ 工具链和标准之间的兼容性,Zephyr 头文件中的指定
初始化器应遵循所有 C++20 规则和限制。非指定的、C99 之前的初始化提供了更多的
兼容性,也是允许的,但指定初始化是更易读和首选的代码风格。在任何情况下,
两种风格都不能在同一个初始化器中混合。

警告:成功编译并不是不兼容性故事的结束。例如,初始化器表达式的 *求值顺序* 在 C99
中未指定!在 C++20 中是(预期的)从左到右的顺序。其他标准修订版可能有所不同。
如有疑问,不要依赖求值顺序(此处和其他地方)。

匿名联合
----------------

匿名联合(也称为"未命名"联合)似乎从 C++ 一开始就是其一部分。它们直到 C11 才
正式添加到 C 中。像往常一样,C 和 C++ 之间存在差异。例如,C 仅支持匿名联合作为
封闭 ``struct`` 或 ``union`` 的成员,空列表 ``{ }`` 在 C++ 中一直是允许的,
但它们需要 C23 等。

初始化匿名成员时,表达式可以用大括号括起来,也可以不括起来。它可以是指定的或裸的。
为了最大的可移植性,初始化 *匿名联合* 时:

- *不要* 用大括号括起 *指定的* 初始化器。这是 C++20 及更高版本所要求的,
  它们将此类大括号视为将裸表达式与(其他)指定初始化器混合,并且无法编译。

- *要* 用大括号括起 *裸* 表达式。这是 C 所要求的。也许是因为 C 更宽松,
  允许许多初始化可能性和变体,所以它可能需要这些大括号来消除歧义?
  请注意,C 确实允许在初始化器表达式中省略大多数大括号 - 但在使用裸表达式
  初始化匿名联合的这种特殊情况下不允许。

一些 C11 之前的 GCC 版本支持某种形式的匿名联合。不幸的是,它们需要用大括号括起
它们的指定初始化器,这与此建议冲突。这可以通过 ``#ifdef __STDC_VERSION__`` 解决,
如 Zephyr 提交 `c15f029a7108
<https://github.com/zephyrproject-rtos/zephyr/commit/c15f029a7108>`_ 和
相应的代码审查所示。
