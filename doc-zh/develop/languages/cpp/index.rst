C++ 语言支持
###########

C++ 是一种基于 C 语言的通用面向对象编程语言。

启用 C++ 支持
*************

Zephyr 支持用 C 和 C++ 编写的应用程序。但是，要在应用程序中使用 C++，
必须配置 Zephyr 以包含 C++ 支持，方法是在应用程序配置文件中选择
:kconfig:option:`CONFIG_CPP`。

要启用 C++ 支持，编译器工具链还必须包含 C++ 编译器，并且包含的编译器必须受 Zephyr 构建系统支持。
:ref:`toolchain_zephyr_sdk`（包括 GNU C++ 编译器（GCC 的一部分））受 Zephyr 支持，
此处记录的功能及其可用性假设使用 Zephyr SDK。

Zephyr 应用程序的默认 C++ 标准级别（即编译器标志强制执行的语言）是 C++11。
其他标准可通过 kconfig 选择获得，例如 :kconfig:option:`CONFIG_STD_CPP98`。
Zephyr 中支持和测试的最旧标准是 C++98。

编译源文件时，构建系统根据文件的后缀（扩展名）选择 C++ 编译器。
使用 **cpp** 或 **cxx** 后缀的文件使用 C++ 编译器编译。例如，
:file:`myCplusplusApp.cpp` 使用 C++ 编译。

C++ 标准要求 ``main()`` 函数的返回类型为 ``int``。
你的 ``main()`` 必须定义为 ``int main(void)`` 或 ``int main(int, char **)``。
要使用带参数的 main，必须选择 ``CONFIG_BOOTARGS`` 选项。Zephyr 忽略 main 的返回值，
因此应用程序不应返回状态信息，应该返回零。

.. note::
    不要对内核、驱动程序或系统初始化代码使用 C++。

语言功能
*******

Zephyr 目前仅提供 C++ 功能的子集。不支持以下功能：

* 静态全局对象析构
* 特定于操作系统的 C++ 标准库类（例如 ``std::thread``、``std::mutex``）

虽然不是详尽的列表，但支持以下功能：

* 继承
* 虚函数
* 虚表
* 静态全局对象构造器
* 使用 **new** 和 **delete** 操作符进行动态对象管理
* 异常
* :abbr:`RTTI（运行时类型信息）`
* 标准模板库（STL）

静态全局对象构造器在驱动程序初始化后但在应用程序 :c:func:`main()` 函数之前初始化。
因此，C++ 的使用仅限于应用程序代码。

为了使用 C++ 异常，必须在应用程序配置文件中选择
:kconfig:option:`CONFIG_CPP_EXCEPTIONS`。

Zephyr 最小 C++ 库
******************

Zephyr 最小 C++ 库（:file:`lib/cpp/minimal`）提供了 C++ 标准库和应用程序二进制接口（ABI）
函数的最小子集，以启用基本的 C++ 语言支持。这包括：

* ``new`` 和 ``delete`` 操作符
* 虚函数 stub 和虚表
* 全局构造器的静态全局初始化器

最小 C++ 库的范围严格限于提供基本的 C++ 语言支持，它不实现任何
`标准模板库（STL）`_ 类和函数。因此，它仅适合用于实现自己的（非标准）类库的应用程序，
并且不依赖标准模板库（STL）组件。

任何使用标准模板库（STL）组件（如 ``std::string`` 和 ``std::vector``）的应用程序
都必须启用 C++ 标准库支持。

C++ 标准库
*********

`C++ 标准库`_ 是 ISO C++ 标准（``std`` 命名空间）的一部分的类和函数的集合。

Zephyr 不包括任何 C++ 标准库实现的源代码形式。相反，它允许配置构建系统以链接到
C++ 编译器工具链中包含的预构建 C++ 标准库。

要启用 C++ 标准库，请从应用程序配置文件中的 :kconfig:option:`CONFIG_LIBCPP_IMPLEMENTATION`
中选择适用的工具链特定 C++ 标准库类型。

例如，使用 :ref:`toolchain_zephyr_sdk` 构建时，构建系统可以配置为链接到 GNU C++ 库（``libstdc++.a``），
这是一个功能完整的 C++ 标准库，提供 ISO C++ 标准所需的所有功能，包括标准模板库（STL），
通过在应用程序配置文件中选择 :kconfig:option:`CONFIG_GLIBCXX_LIBCPP` 来实现。

Zephyr 支持以下 C++ 标准库：

* GNU C++ 库（:kconfig:option:`CONFIG_GLIBCXX_LIBCPP`）
* ARC MetaWare C++ 库（:kconfig:option:`CONFIG_ARCMWDT_LIBCPP`）

需要完整 C++ 标准库功能的 Zephyr 子系统可以从其配置中选择
:kconfig:option:`CONFIG_REQUIRES_FULL_LIBCPP`，这会自动选择兼容的 C++ 标准库，
除非选择了特定 C++ 标准库的 Kconfig 符号。

C 和 C++ 之间的头文件和不兼容性
*****************************

要彼此交互，C 和 C++ 必须通过头文件共享代码：数据结构、宏、静态函数等。
虽然 C 和 C++ 有很大的重叠，但它们是不同的语言，具有 `已知的不兼容性`_。
C 不仅仅是 C++ 的子集。标准级别（例如："C+11"）增加了另一层复杂性，
因为新功能通常受另一种语言启发并从中复制，但许多年后，存在细微差异。
为了使事情更加复杂，编译器通常在标准化之前提供功能的早期原型。
标准可能有不同编译器解释不同的歧义。编译器可能有错误，这些可能需要解决方法。
为了解决这个问题，许多项目限制自己使用有限数量的工具链。Zephyr 没有。

这些兼容性问题对头文件的影响不成比例。不仅因为它们必须在 C 和 C++ 之间兼容，
而且因为由于 *间接* 包含和 `缺乏结构和头文件组织`_ 而具有的典型的真实世界项目，
它们最终被编译在令人惊讶的大量其他源文件中。因此，头文件暴露于更大的工具链种类和项目配置。

添加更多约束，Zephyr 项目在代码风格、编译器警告、静态分析器和标准合规性（例如：MISRA）
方面具有苛刻的策略。

总之，所有这些约束可以使编写头文件非常具有挑战性。本节的目的是记录一些最佳"头文件做法"
和 Zephyr 特定上下文中的经验教训。虽然这里的许多信息不是 Zephyr 特定的，
但本节不是 C/C++ 标准、教科书和其他参考资料知识的替代品。

测试
----

幸运的是，Zephyr 项目具有广泛的测试和 CI 基础设施，提供覆盖率基线、
早期发现问题、执行策略并在某种控制下维护此类组合爆炸。
``tests/lib/cpp/cxx/`` 在这方面非常有用，因为它们的 ``testcase.yaml`` 配置
让 ``twister`` 快速迭代一系列 ``-std`` 参数：``-std=c++98``、``-std=c++11`` 等。

请记住，未使用的宏不会被编译。

指定的初始化器
--------------

初始化宏在头文件中很常见，因为它们有助于减少样板代码。C99 添加了
通过"指定"成员名称而不是 *裸* 表达式列表来初始化 ``struct`` 和 ``union`` 类型。
某些 GCC 版本即使在其 C90 模式下也支持指定的初始化器。

在简单级别使用时，指定的初始化器不易出错、可读性更强且更灵活。
另一方面，C99 允许令人惊讶的大量和宽松的可能性：指定的初始化器可以无序、
重复、"嵌套"（``.a.x =``）、各种其他大括号可以省略、指定的初始化器和不能混合等。

二十年后，C++20 将指定的初始化器添加到 C++，但方式更受限制；
部分原因是 C++ ``struct`` 实际上是 ``class``。如下所述的 C++ 提案编号 P0329
（与 C 相比）或任何完整的 C++ 参考，混合是不允许的，初始化器必须按顺序排列（允许间隙）。

有趣的是，C++20 中的新限制可能会导致 ``gcc -std=c++20`` 无法编译使用
``gcc -std=c++17`` 成功编译的代码。例如，``gcc -std=c++17`` 及更早版本允许
初始化器和裸表达式的 C 风格混合。这无法使用相同 GCC 版本的 ``gcc -std=c++20`` 编译。

建议：为了在不同的 C 和 C++ 工具链和标准中最大化兼容性，Zephyr 头文件中的
指定初始化器应遵循所有 C++20 规则和限制。非指定的、pre-C99 初始化提供了更多兼容性，
也是允许的，但指定的初始化是更可读和首选的代码风格。在任何情况下，
两种风格都必须从不在同一初始化器中混合。

警告：成功编译不是不兼容故事的结束。例如，初始化器表达式的 *评估顺序*
在 C99 中是未指定的！在 C++20 中是（预期的）从左到右的顺序。
其他标准版本可能有所不同。如有疑问，不要依赖评估顺序（这里和其他地方）。

匿名联合
--------

匿名联合（也称为"未命名"联合）似乎从一开始就是 C++ 的一部分。
它们直到 C11 才正式添加到 C。通常，C 和 C++ 之间存在差异。例如，
C 仅支持将匿名联合作为封闭 ``struct`` 或 ``union`` 的成员、空列表 ``{ }``
一直允许在 C++ 中，但它们需要 C23 等。

初始化匿名成员时，表达式可以用大括号括起来，也可以不括起来。
它可以是指定的或裸的。为了最大的可移植性，初始化 *匿名联合* 时：

- 不要用大括号括起 *指定的* 初始化器。这是 C++20 及以上版本所需的，
  它将此类大括号视为混合裸表达式与（其他）指定初始化器，并无法编译。

- 用大括号括起 *裸* 表达式。这是 C 所需的。也许因为 C 更宽松并允许许多初始化可能性和变体，
  所以它可能需要这样的大括号来消除歧义？请注意 C 确实允许在初始化器表达式中省略大多数大括号 - 但在
  初始化匿名联合的这种特定情况下不允许。

某些 pre-C11 GCC 版本支持某种形式的匿名联合。不幸的是，
它们需要用大括号括起其指定的初始化器，这与此建议相冲突。
这可以通过 ``#ifdef __STDC_VERSION__`` 来解决，如 Zephyr 提交
`c15f029a7108 <https://github.com/zephyrproject-rtos/zephyr/commit/c15f029a7108>`_
和相应的代码审查中所示。
